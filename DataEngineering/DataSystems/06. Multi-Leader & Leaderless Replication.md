Replication with Multi-Leaders or Leaderless

다중 리더(Multi-Leader) 또는 리더리스(Leaderless) 복제

Multi-leaders Replication

다중 리더 복제(Multi-Leader Replication)

Multi-Leader Replication (also known as "master-master replication") is a replication model where multiple database nodes act as leaders (or masters), allowing them to accept and process write requests simultaneously.
다중 리더 복제(Master-Master Replication)는 여러 데이터베이스 노드가 동시에 리더(또는 마스터) 역할을 수행하여, 여러 노드가 동시에 쓰기 요청을 받아 처리할 수 있는 복제 방식이다.
Key Characteristics of Multi-Leader Replication

다중 리더 복제의 주요 특징

Multiple Write Nodes
여러 개의 쓰기 노드(Multiple Write Nodes)
Conflict Handling
충돌 처리(Conflict Handling)
Since writes can occur simultaneously on different nodes, conflicts may arise (e.g., concurrent updates to the same data). Conflict resolution strategies (e.g., last-write-wins, custom merge logic) must be implemented to handle these issues.
서로 다른 노드에서 동시에 쓰기가 발생할 수 있으므로 충돌이 발생할 수 있다. (예: 동일한 데이터에 대한 동시 업데이트) 이러한 문제를 해결하기 위해 Last-Write-Wins, Custom Merge Logic과 같은 충돌 해결 전략을 구현해야 한다.
Increased Availability
높은 가용성(Increased Availability)
Geographical Distribution
지역 분산(Geographical Distribution)
Useful for multiple data center
여러 데이터센터 환경에서 유용하다.
Asynchronous Replication
비동기 복제(Asynchronous Replication)
Changes made on one leader are propagated to others in the background (i.e. eventual consistency)
한 리더에서 발생한 변경 사항은 백그라운드에서 다른 리더로 전파된다. (즉, 최종 일관성(Eventual Consistency)을 제공한다.)
Use Cases for Multi-Leader Replication

다중 리더 복제의 활용 사례

Collaborative Applications
협업 애플리케이션(Collaborative Applications)
Real-time collaborative platforms (like document editing tools) where users may make simultaneous edits from different locations.
문서 편집 도구와 같은 실시간 협업 플랫폼에서, 서로 다른 위치의 사용자가 동시에 문서를 수정하는 경우에 적합하다.
High Availability Systems
고가용성 시스템(High Availability Systems)
Systems that require continuous availability and can't afford downtime during leader node failures.
리더 노드에 장애가 발생하더라도 서비스 중단 없이 지속적으로 운영되어야 하는 시스템에 적합하다.
Geo-Distributed Databases
지역 분산 데이터베이스(Geo-Distributed Databases)
Situations where data is spread across multiple regions, and low-latency writes are needed in all locations.
데이터가 여러 지역에 분산되어 있고, 모든 지역에서 낮은 지연 시간으로 쓰기 작업을 수행해야 하는 환경에 적합하다.
Challenges with Multi-Leader Replication

다중 리더 복제의 과제

Conflict Resolution
충돌 해결(Conflict Resolution)
Handling conflicts effectively can be complex, depending on the use case.
사용 사례에 따라 충돌을 효과적으로 해결하는 과정이 매우 복잡할 수 있다.
e.g auto incremental keys, triggers, foreign key constraints and more
예: 자동 증가 키(Auto Increment Key), 트리거(Trigger), 외래 키(Foreign Key) 제약 조건 등
Data Consistency
데이터 일관성(Data Consistency)
Achieving strong consistency is difficult due to the asynchronous nature and the potential for conflicting writes.
비동기 복제 방식과 동시 쓰기 충돌 가능성 때문에 강한 일관성(Strong Consistency)을 보장하기 어렵다.
Network Partitioning
네트워크 분할(Network Partitioning)
Partitions can lead to temporary inconsistencies if one or more leader nodes are isolated.
하나 이상의 리더 노드가 네트워크에서 분리되면 일시적인 데이터 불일치가 발생할 수 있다.

User Intervention

사용자 개입(User Intervention)

In cases where automatic resolution might not be feasible (e.g., complex business logic), user intervention may be needed.
자동으로 충돌을 해결하기 어려운 경우(예: 복잡한 비즈니스 로직)에는 사용자의 개입이 필요할 수 있다.
The system flags conflicts for manual review, allowing users to select which version to keep or how to merge changes.
시스템은 충돌을 표시하여 사용자가 직접 어떤 버전을 유지할지 또는 어떻게 병합할지를 선택하도록 한다.

장점

복잡한 상황에서도 정확하게 충돌을 해결할 수 있다.

단점

사람이 직접 개입해야 하므로 처리 속도가 느리고 자동화 수준이 낮아진다.

Last Write Wins (LWW)

마지막 쓰기 우선(Last Write Wins, LWW)

This is a simple, timestamp-based conflict resolution strategy where the latest write is accepted, and conflicting writes are discarded.
가장 최근에 수행된 쓰기를 채택하고, 이전의 충돌하는 쓰기는 버리는 단순한 타임스탬프 기반 충돌 해결 방식이다.
It's implemented using timestamps or version numbers, where the database retains the value with the most recent timestamp.
타임스탬프 또는 버전 번호를 사용하며, 가장 최신 타임스탬프를 가진 값을 데이터베이스에 유지한다.
Pros

장점

Easy to implement and understand.
구현과 이해가 쉽다.
Cons

단점

Data loss can occur if valuable updates are overwritten by newer, less meaningful changes.
더 의미 있는 데이터가 단순히 더 늦게 작성된 데이터에 의해 덮어써져 데이터 손실이 발생할 수 있다.

Custom Merge Logic

사용자 정의 병합 로직(Custom Merge Logic)

Custom merge logic allows users to define their own conflict resolution rules based on business requirements.
비즈니스 요구사항에 맞게 사용자가 직접 충돌 해결 규칙을 정의할 수 있다.
For example, in collaborative editing, conflicting changes might be merged by combining the text from both changes.
예를 들어 협업 문서 편집에서는 서로 충돌하는 변경 사항을 두 내용을 모두 반영하여 병합할 수 있다.
Pros

장점

Provides tailored solutions that maintain data quality and business logic.
데이터 품질과 비즈니스 로직을 유지할 수 있는 맞춤형 해결 방식을 제공한다.
Cons

단점

Complex to implement, requiring detailed understanding of business rules.
비즈니스 규칙을 깊이 이해해야 하므로 구현이 복잡하다.

Conflict-Free Replicated Data Types (CRDTs)

충돌 없는 복제 데이터 타입(CRDTs)

CRDTs are special data structures designed to automatically resolve conflicts in distributed systems.
CRDT는 분산 시스템에서 충돌을 자동으로 해결하도록 설계된 특수한 데이터 구조이다.
They work by ensuring that all updates can be merged together without ambiguity, often by defining rules for merging operations.
모든 업데이트를 모호함 없이 병합할 수 있도록 동작하며, 일반적으로 병합 규칙을 미리 정의한다.
Example CRDTs include counters, sets, and maps that merge conflicting updates deterministically.
대표적인 CRDT에는 Counter, Set, Map 등이 있으며, 충돌하는 업데이트를 결정적으로 병합할 수 있다.
Pros

장점

Offers mathematically guaranteed convergence of replicated states.
복제된 데이터가 수학적으로 동일한 상태로 수렴함을 보장한다.
Cons

단점

Limited to use cases that can benefit from data structures that fit into the CRDT model.
CRDT 모델에 적합한 데이터 구조를 사용하는 경우에만 적용할 수 있다는 한계가 있다.

Operational Transformation (OT)

운영 변환(Operational Transformation, OT)

OT is commonly used in collaborative applications, like real-time document editing, where concurrent changes are transformed to maintain a consistent end state.
OT는 실시간 문서 편집과 같은 협업 애플리케이션에서 주로 사용되며, 동시에 발생한 변경 사항을 변환하여 최종 결과가 일관되도록 만든다.
It reorders and modifies operations to achieve the same final result across all replicas.
모든 복제본이 동일한 최종 결과를 갖도록 작업의 순서를 조정하거나 수정한다.
Pros

장점

Effective for collaborative, real-time applications.
실시간 협업 애플리케이션에서 효과적으로 사용할 수 있다.
Cons

단점

Complex to implement and computationally intensive.
구현이 복잡하며 계산 비용이 많이 든다.

Version Vectors

버전 벡터(Version Vectors)

Version vectors are used to keep track of versions of data across replicas, identifying which changes were applied and which are missing.
버전 벡터는 여러 복제본(Replica) 간 데이터의 버전을 추적하여, 어떤 변경 사항이 적용되었고 어떤 변경 사항이 누락되었는지를 식별하는 데 사용된다.
They help determine the order of conflicting writes and apply appropriate resolution logic (e.g., merging, rejecting, or applying one update over the other).
충돌하는 쓰기의 순서를 판단하고, 병합(Merging), 거부(Rejecting), 특정 업데이트 적용 등 적절한 충돌 해결 로직을 적용하는 데 도움을 준다.
Pros

장점

Allows precise tracking of conflicts and their resolution.
충돌과 그 해결 과정을 정확하게 추적할 수 있다.
Cons

단점

Can become complex in large distributed systems with many concurrent writes.
동시 쓰기가 많은 대규모 분산 시스템에서는 매우 복잡해질 수 있다.

Prevention Strategies

충돌 예방 전략(Prevention Strategies)

In addition to resolving conflicts, some systems focus on conflict prevention, such as partitioning data ownership across leaders, ensuring that writes for specific records are directed to designated leaders.
일부 시스템은 충돌을 해결하는 것뿐만 아니라, 리더 간 데이터 소유권을 분할하여 특정 레코드의 쓰기 요청이 지정된 리더로만 전달되도록 함으로써 충돌을 예방한다.
This reduces the chances of conflicts by limiting concurrent writes to the same data.
동일한 데이터에 대한 동시 쓰기를 제한하여 충돌 발생 가능성을 줄인다.
Pros

장점

Reduces the frequency of conflicts and the need for resolution.
충돌 발생 빈도와 충돌 해결의 필요성을 줄일 수 있다.
Cons

단점

Requires careful design of data distribution and routing logic.
데이터 분산 방식과 라우팅 로직을 신중하게 설계해야 한다.

Application-Level Logic

애플리케이션 수준 로직(Application-Level Logic)

Some conflicts can be better handled at the application level, where developers can apply domain-specific rules for merging data.
일부 충돌은 애플리케이션 수준에서 처리하는 것이 더 적합하며, 개발자는 도메인에 특화된 규칙을 적용하여 데이터를 병합할 수 있다.
For instance, banking applications might sum concurrent deposits to the same account rather than choosing one over the other.
예를 들어, 은행 시스템에서는 동일한 계좌에 동시에 입금된 금액을 하나만 선택하는 대신 모두 합산하여 처리할 수 있다.
Pros

장점

Allows domain-specific rules to be directly implemented.
도메인에 특화된 비즈니스 규칙을 직접 구현할 수 있다.
Cons

단점

Increases complexity at the application layer.

Leaderless Replication

리더리스 복제(Leaderless Replication)

There is no designated "leader" or "primary" node for handling writes and coordination. Instead, all nodes in the system are equal and can independently handle read and write requests.
쓰기 작업과 조정을 담당하는 지정된 리더(Leader) 또는 프라이머리(Primary) 노드가 존재하지 않는다. 대신 시스템의 모든 노드는 동등한 역할을 가지며, 독립적으로 읽기와 쓰기 요청을 처리할 수 있다.
Key Characteristics of Leaderless Replication

리더리스 복제의 주요 특징

No Single Point of Failure
단일 장애 지점(Single Point of Failure)이 없다.
Decentralized Writes
분산된 쓰기(Decentralized Writes)
Clients can write to multiple nodes simultaneously (often a subset of nodes)
클라이언트는 여러 노드(보통 일부 노드 집합)에 동시에 쓰기 요청을 보낼 수 있다.
Eventual Consistency
최종 일관성(Eventual Consistency)
Quorum-based Read and Write
쿼럼 기반 읽기 및 쓰기(Quorum-based Read and Write)
Quorum Writes (W): Data is considered written if it is successfully stored on at least a quorum number of nodes.
쿼럼 쓰기(W): 데이터가 최소한 쿼럼 수 이상의 노드에 저장되면 쓰기가 성공한 것으로 간주한다.
Quorum Reads (R): Data is considered read successfully if it is retrieved from a quorum of nodes.
쿼럼 읽기(R): 데이터가 쿼럼 수 이상의 노드에서 조회되면 읽기가 성공한 것으로 간주한다.
The sum of read and write quorum values (R + W) should be greater than the total number of replicas (N) to ensure consistency.
일관성을 보장하기 위해 읽기 쿼럼(R)과 쓰기 쿼럼(W)의 합(R + W)은 전체 복제본 수(N)보다 커야 한다.

Handling Conflicts

충돌 처리(Handling Conflicts)

Vector clocks to detect conflicting versions of data.
Vector Clock을 사용하여 데이터의 충돌하는 버전을 감지한다.
Read repair during reads to correct inconsistencies.
읽기(Read) 과정에서 Read Repair를 수행하여 데이터 불일치를 수정한다.
Hinted handoff for temporarily unavailable nodes to ensure eventual consistency.
일시적으로 사용할 수 없는 노드를 위해 Hinted Handoff를 사용하여 최종 일관성을 보장한다.
Advantages of Leaderless Replication

리더리스 복제의 장점

High Availability
높은 가용성(High Availability)
The absence of a leader node makes the system highly available, even under node failures or network partitions.
리더 노드가 없기 때문에 노드 장애나 네트워크 분할 상황에서도 높은 가용성을 유지할 수 있다.
Fault Tolerance
장애 허용성(Fault Tolerance)
Since all nodes are peers, the failure of one or more nodes does not prevent read or write operations.
모든 노드가 동등한 역할을 수행하므로 일부 노드에 장애가 발생해도 읽기와 쓰기 작업을 계속 수행할 수 있다.
Scalability
확장성(Scalability)
It's easier to scale horizontally because all nodes handle the same tasks, reducing bottlenecks typically seen with leader-based models.
모든 노드가 동일한 역할을 수행하므로 수평 확장이 쉽고, 리더 기반 모델에서 발생하는 병목 현상을 줄일 수 있다.
Reduced Latency
낮은 지연 시간(Reduced Latency)
Clients can write to or read from the closest available nodes, reducing latency, especially in geo-distributed deployments.
클라이언트는 가장 가까운 노드에서 읽기와 쓰기를 수행할 수 있어, 특히 지역 분산 환경에서 지연 시간을 줄일 수 있다.
Challenges with Leaderless Replication

리더리스 복제의 과제

Consistency Trade-offs
일관성 트레이드오프(Consistency Trade-offs)
Achieving strong consistency is challenging, as the model is optimized for availability and partition tolerance (following the CAP theorem).
이 모델은 CAP 이론에 따라 가용성과 분할 허용성을 우선하기 때문에 강한 일관성(Strong Consistency)을 보장하기 어렵다.
Applications must tolerate temporary inconsistencies.
애플리케이션은 일시적인 데이터 불일치를 허용할 수 있어야 한다.
Conflict Resolution Complexity
충돌 해결의 복잡성(Conflict Resolution Complexity)
Handling conflicts across nodes requires careful design, often at the application level or with complex resolution algorithms (e.g., merging concurrent versions).
노드 간 충돌을 해결하려면 신중한 설계가 필요하며, 일반적으로 애플리케이션 수준의 처리 또는 복잡한 충돌 해결 알고리즘(예: 동시 버전 병합)이 요구된다.
Quorum Imbalance
쿼럼 불균형(Quorum Imbalance)
If quorum values are misconfigured (e.g., low write quorum), it can lead to inconsistent reads or lost writes.
쿼럼 값이 잘못 설정되면(예: 낮은 쓰기 쿼럼) 데이터 불일치나 쓰기 손실이 발생할 수 있다.
