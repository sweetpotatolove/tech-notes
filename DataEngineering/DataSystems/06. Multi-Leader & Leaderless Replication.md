# Multi-Leaders & Leaderless Replication
## 다중 리더 복제(Multi-Leader Replication)
### 다중 리더 복제(Master-Master Replication)
- 여러 데이터베이스 노드가 동시에 리더(또는 마스터) 역할을 수행하여, **여러 노드가 동시에 쓰기 요청을 받아 처리할 수 있는 복제 방식**

    ![alt text](image-26.png)
    - ex. 미국에 서비스 제공할 때
        - WEST가 있고, EAST가 있을 것
        - 서부의 서비스를 동일하게 동부에
        - 하나의 DB에 Leader, Folower가 하나씩 있음
        - 각 지역에서 동시에 여러 사람이 Leader와 이야기함 - sync 사용
        - 데이터 센터 간 Replication이 일어날 땐 async 사용
        - conflict Resolution: 동일한 데이터 엑세스할 때 문제 생길 수 있는데, 리더가 팔로워한테 복제해주고, 다른 DC에 넘길 때 리더한테 바로 가는게 아니라 conflict 거쳐서 감??

- 다중 리더 복제의 주요 특징
    - 여러 개의 쓰기 노드(Multiple Write Nodes)
    - 충돌 처리(Conflict Handling)
        - 서로 다른 노드에서 동시에 쓰기가 발생할 수 있으므로 충돌이 발생할 수 있음
        - ex. 동일한 데이터에 대한 동시 업데이트
        - 이러한 문제를 해결하기 위해 Last-Write-Wins, Custom Merge Logic과 같은 충돌 해결 전략을 구현해야 함
    - 높은 가용성(Increased Availability)
    - 지역 분산(Geographical Distribution)
        - 여러 데이터센터 환경에서 유용함
    - 비동기 복제(Asynchronous Replication)
        - 한 리더에서 발생한 변경 사항은 백그라운드에서 다른 리더로 전파됨
        - 즉, 최종 일관성(Eventual Consistency)을 제공한
        - propagated: 어떤 change가 일어났을 때 apply하는 시간을 .. 뭐라노

- 다중 리더 복제의 활용 사례
    - 협업 애플리케이션(Collaborative Applications)
        - 문서 편집 도구와 같은 실시간 협업 플랫폼에서, 서로 다른 위치의 사용자가 동시에 문서를 수정하는 경우에 적합함
    - 고가용성 시스템(High Availability Systems)
        - 리더 노드에 장애가 발생하더라도 서비스 중단 없이 지속적으로 운영되어야 하는 시스템에 적합함
    - 지역 분산 데이터베이스(Geo-Distributed Databases)
        - 데이터가 여러 지역에 분산되어 있고, 모든 지역에서 낮은 지연 시간으로 쓰기 작업을 수행해야 하는 환경에 적합함
    
- 다중 리더 복제의 과제
    - 충돌 해결(Conflict Resolution)
        - 사용 사례에 따라 충돌을 효과적으로 해결하는 과정이 매우 복잡할 수 있음
        - ex. 자동 증가 키(Auto Increment Key), 트리거(Trigger), 외래 키(Foreign Key) 제약 조건 등
    - 데이터 일관성(Data Consistency)
        - 비동기 복제 방식과 동시 쓰기 충돌 가능성 때문에 강한 일관성(Strong Consistency)을 보장하기 어려움
    - 네트워크 분할(Network Partitioning)
        - 하나 이상의 리더 노드가 네트워크에서 분리되면 일시적인 데이터 불일치가 발생할 수 있음


### 다중 리더 복제에서의 충돌 시 해결 방법
- 사용자 개입(User Intervention)
    - 자동으로 충돌을 해결하기 어려운 경우(ex. 복잡한 비즈니스 로직)에는 사용자의 개입이 필요할 수 있음
    - 시스템은 충돌을 표시하여 사용자가 직접 어떤 버전을 유지할지 또는 어떻게 병합할지를 선택하도록 함
    - 장점
        - 복잡한 상황에서도 정확하게 충돌을 해결할 수 있음
    - 단점
        - 사람이 직접 개입해야 하므로 처리 속도가 느리고 자동화 수준이 낮아짐

- 마지막 쓰기 우선(Last Write Wins, LWW)
    - **가장 최근에 수행된 쓰기를 채택하고, 이전의 충돌하는 쓰기는 버리는** 단순한 타임스탬프 기반 충돌 해결 방식
    - **타임스탬프 또는 버전 번호를 사용**하며, 가장 최신 타임스탬프를 가진 값을 데이터베이스에 유지함
    - 장점
        - 구현과 이해가 쉬움
    - 단점
        - 더 의미 있는 데이터가 단순히 더 늦게 작성된 데이터에 의해 덮어써져 데이터 손실이 발생할 수 있음

- 사용자 정의 병합 로직(Custom Merge Logic)
    - 비즈니스 요구사항에 맞게 **사용자가 직접 충돌 해결 규칙을 정의할 수 있음**
    - ex. 협업 문서 편집에서는 서로 충돌하는 변경 사항을 두 내용을 모두 반영하여 병합할 수 있음
    - 장점
        - 데이터 품질과 비즈니스 로직을 유지할 수 있는 맞춤형 해결 방식을 제공함
    - 단점
        - 비즈니스 규칙을 깊이 이해해야 하므로 구현이 복잡함

- 충돌 없는 복제 데이터 타입(CRDTs)
    - CRDT는 분산 시스템에서 충돌을 자동으로 해결하도록 설계된 특수한 데이터 구조
    - 모든 업데이트를 모호함 없이 병합할 수 있도록 동작하며, 일반적으로 병합 규칙을 미리 정의함
    - 대표적인 CRDT에는 Counter, Set, Map 등이 있으며, 충돌하는 업데이트를 결정적으로 병합할 수 있음
    - 장점
        - 복제된 데이터가 수학적으로 동일한 상태로 수렴함을 보장함
    - 단점
        - CRDT 모델에 적합한 데이터 구조를 사용하는 경우에만 적용할 수 있다는 한계가 있음
    
- 운영 변환(Operational Transformation, OT)
    - OT는 실시간 문서 편집과 같은 협업 애플리케이션에서 주로 사용되며, 동시에 발생한 변경 사항을 변환하여 최종 결과가 일관되도록 만듦
    - 모든 복제본이 동일한 최종 결과를 갖도록 작업의 순서를 조정하거나 수정함
    - 장점
        - 실시간 협업 애플리케이션에서 효과적으로 사용할 수 있음
    - 단점
        - 구현이 복잡하며 계산 비용이 많이 듦

- 버전 벡터(Version Vectors)
    - 버전 벡터는 여러 복제본(Replica) 간 데이터의 버전을 추적하여, 어떤 변경 사항이 적용되었고 어떤 변경 사항이 누락되었는지를 식별하는 데 사용됨
    - 충돌하는 쓰기의 순서를 판단하고, 병합(Merging), 거부(Rejecting), 특정 업데이트 적용 등 적절한 충돌 해결 로직을 적용하는 데 도움을 줌
    - 장점
        - 충돌과 그 해결 과정을 정확하게 추적할 수 있음
    - 단점
        - 동시 쓰기가 많은 대규모 분산 시스템에서는 매우 복잡해질 수 있음
    
- 충돌 예방 전략(Prevention Strategies)
    - 일부 시스템은 충돌을 해결하는 것뿐만 아니라, 리더 간 데이터 소유권을 분할하여 **특정 레코드의 쓰기 요청이 지정된 리더로만 전달되도록** 함으로써 충돌을 예방함
    - 동일한 데이터에 대한 동시 쓰기를 제한하여 충돌 발생 가능성을 줄임
    - 장점
        - 충돌 발생 빈도와 충돌 해결의 필요성을 줄일 수 있음
    - 단점
        - 데이터 분산 방식과 라우팅 로직을 신중하게 설계해야 함
    
- 애플리케이션 수준 로직(Application-Level Logic)
    - 일부 충돌은 애플리케이션 수준에서 처리하는 것이 더 적합하며, 개발자는 도메인에 특화된 규칙을 적용하여 데이터를 병합할 수 있음
    - ex. 은행 시스템에서는 동일한 계좌에 동시에 입금된 금액을 하나만 선택하는 대신 모두 합산하여 처리할 수 있음
    - 장점
        - 도메인에 특화된 비즈니스 규칙을 직접 구현할 수 있음
    - 단점
        - 애플리케이션 계층의 복잡도가 증가함


## 리더리스 복제(Leaderless Replication)
### 리더리스 복제(Leaderless Replication)
- 쓰기 작업과 조정을 담당하는 지정된 **리더(Leader) 또는 프라이머리(Primary) 노드가 존재하지 않음**
- 대신 시스템의 모든 노드는 동등한 역할을 가지며, 독립적으로 읽기와 쓰기 요청을 처리할 수 있음

- 리더리스 복제의 주요 특징
    - 단일 장애 지점(Single Point of Failure)이 없음
    - 분산된 쓰기(Decentralized Writes)
        - 클라이언트는 여러 노드(보통 일부 노드 집합)에 동시에 쓰기 요청을 보낼 수 있음
    - 최종 일관성(Eventual Consistency)
    - 쿼럼 기반 읽기 및 쓰기(Quorum-based Read and Write)
        - Quorum Writes (W): 데이터가 최소한 쿼럼 수 이상의 노드에 저장되면 쓰기가 성공한 것으로 간주함
        - Quorum Reads (R): 데이터가 쿼럼 수 이상의 노드에서 조회되면 읽기가 성공한 것으로 간주함
        - 일관성을 보장하기 위해 읽기 쿼럼(R)과 쓰기 쿼럼(W)의 **합(R + W)은 전체 복제본 수(N)보다 커야함**
    - 충돌 처리(Handling Conflicts)
        - **Vector Clock** 을 사용하여 데이터의 충돌하는 버전을 감지
        - **읽기(Read) 과정에서 Read Repair를 수행**하여 데이터 불일치를 수정
        - 일시적으로 사용할 수 없는 노드를 위해 **Hinted Handoff**를 사용하여 최종 일관성을 보장함

- 리더리스 복제의 장점
    - 높은 가용성(High Availability)
        - 리더 노드가 없기 때문에 노드 장애나 네트워크 분할 상황에서도 높은 가용성을 유지할 수 있음
    - 장애 허용성(Fault Tolerance)
        - 모든 노드가 동등한 역할을 수행하므로 일부 노드에 장애가 발생해도 읽기와 쓰기 작업을 계속 수행할 수 있음
    - 확장성(Scalability)
        - 모든 노드가 동일한 역할을 수행하므로 수평 확장이 쉽고, 리더 기반 모델에서 발생하는 병목 현상을 줄일 수 있음
    - 낮은 지연 시간(Reduced Latency)
        - 클라이언트는 가장 가까운 노드에서 읽기와 쓰기를 수행할 수 있어, 특히 지역 분산 환경에서 지연 시간을 줄일 수 있음

- 리더리스 복제의 과제
    - 일관성 트레이드오프(Consistency Trade-offs)
        - 이 모델은 CAP 이론에 따라 가용성과 분할 허용성을 우선하기 때문에 강한 일관성(Strong Consistency)을 보장하기 어려움
        - 애플리케이션은 일시적인 데이터 불일치를 허용할 수 있어야 함
    - 충돌 해결의 복잡성(Conflict Resolution Complexity)
        - 노드 간 충돌을 해결하려면 신중한 설계가 필요하며, 일반적으로 애플리케이션 수준의 처리 또는 복잡한 충돌 해결 알고리즘(ex. 동시 버전 병합)이 요구됨
    - 쿼럼 불균형(Quorum Imbalance)
        - 쿼럼 값이 잘못 설정되면(예: 낮은 쓰기 쿼럼) 데이터 불일치나 쓰기 손실이 발생할 수 있음

- 리더리스 복제를 사용하는 데이터베이스
    - Amazon DynamoDB
    - Apache Cassandra
    - Riak
