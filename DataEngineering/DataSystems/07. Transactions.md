# The concept of Transaction

# 트랜잭션의 개념

---

## What is Transaction?

## 트랜잭션이란 무엇인가?

- Transaction is a sequence of one or more operations (such as read, write, update, or delete actions) that are executed as a **single logical unit of work.**
- Transactions are **fundamental to ensuring data integrity and consistency within a database**, especially in environments where multiple users or processes might be accessing and modifying the data concurrently.

- 트랜잭션은 하나 이상의 연산(읽기, 쓰기, 수정, 삭제 등)이 **하나의 논리적 작업 단위**로 실행되는 일련의 과정이다.
- 트랜잭션은 **데이터베이스 내에서 데이터의 무결성과 일관성을 보장하는 데 필수적**이며, 특히 여러 사용자나 프로세스가 동시에 데이터에 접근하고 수정할 수 있는 환경에서 중요하다.

---

## ACID Properties - Atomicity

## ACID 속성 - 원자성

- **Atomicity**
  - This ensures that all operations within a transaction are completed successfully.
  - If any part of the transaction fails, the entire transaction is aborted, and the database is left unchanged.
  - In other words, a transaction is **"all or nothing."**

- **원자성**
  - 트랜잭션 내의 모든 연산이 성공적으로 완료되도록 보장한다.
  - 트랜잭션의 어느 한 부분이라도 실패하면 전체 트랜잭션이 중단되며, 데이터베이스는 변경되지 않은 상태로 유지된다.
  - 즉, 트랜잭션은 **"전부 아니면 전무(all or nothing)"**이다.

---

## ACID Properties - Consistency

## ACID 속성 - 일관성

- **Consistency**
  - Transactions must transition the database from **one valid state to another**, maintaining the integrity constraints and rules defined in the database schema.
  - This means that any data written to the database must be valid according to all defined rules, such as data types, triggers, and constraints.

- **일관성**
  - 트랜잭션은 데이터베이스 스키마에 정의된 무결성 제약 조건과 규칙을 유지하면서 데이터베이스를 **하나의 유효한 상태에서 또 다른 유효한 상태로** 전환해야 한다.
  - 이는 데이터베이스에 기록되는 모든 데이터가 데이터 타입, 트리거, 제약 조건 등 정의된 모든 규칙에 따라 유효해야 한다는 것을 의미한다.

---

## ACID Properties - Isolation

## ACID 속성 - 격리성

- **Isolation**
  - This property ensures that **concurrent transactions do not interfere with each other.**
  - Transactions are isolated from one another, so the intermediate state of a transaction is invisible to other transactions.
  - The final outcome appears as if transactions were processed sequentially, even if they were executed concurrently.

- **격리성**
  - 이 속성은 **동시에 실행되는 트랜잭션들이 서로 간섭하지 않도록** 보장한다.
  - 트랜잭션은 서로 격리되어 있으므로, 한 트랜잭션의 중간 상태는 다른 트랜잭션에서 볼 수 없다.
  - 트랜잭션들이 동시에 실행되더라도 최종 결과는 마치 트랜잭션들이 순차적으로 처리된 것처럼 나타난다.

---

## ACID Properties - Durability

## ACID 속성 - 지속성

- **Durability**
  - Once a transaction has been committed, the changes it has made to the database are **permanent**, even in the case of a system failure (such as a power outage or crash).
  - The database system uses various mechanisms, like logging and checkpoints, to ensure that committed transactions are not lost.

- **지속성**
  - 트랜잭션이 한 번 커밋되면 데이터베이스에 적용된 변경 사항은 정전이나 시스템 충돌과 같은 장애가 발생하더라도 **영구적으로 유지된다.**
  - 데이터베이스 시스템은 로깅(logging)과 체크포인트(checkpoint) 등의 다양한 메커니즘을 사용하여 커밋된 트랜잭션이 손실되지 않도록 보장한다.

---

## Example. Bank Balance Transfer

## 예시. 은행 계좌 잔액 이체

- **Atomicity** ensures both debit and credit operations are completed successfully, or neither is executed.
- **Consistency** maintains the total balance across both accounts before and after the transaction.
- **Isolation** prevents other transactions from seeing the intermediate state where $100 has been debited from Account A but not yet credited to Account B.
- **Durability** guarantees that once the transaction is committed, the changes persist, even if the system crashes immediately afterward.

- **원자성(Atomicity)**은 출금과 입금 연산이 모두 성공적으로 완료되거나, 둘 다 실행되지 않도록 보장한다.
- **일관성(Consistency)**은 트랜잭션 전후에 두 계좌의 전체 잔액이 유지되도록 한다.
- **격리성(Isolation)**은 계좌 A에서 $100가 출금되었지만 아직 계좌 B에 입금되지 않은 중간 상태를 다른 트랜잭션이 볼 수 없도록 한다.
- **지속성(Durability)**은 트랜잭션이 커밋된 후 즉시 시스템이 충돌하더라도 변경 사항이 유지되도록 보장한다.


# Single-Object vs. Multi-Object Operations

# 단일 객체 vs. 다중 객체 연산

- Single object (e.g., a single row or document)
- Multiple objects (e.g., multiple rows, documents, or even multiple tables/collections).

- 단일 객체 (예: 하나의 행 또는 문서)
- 다중 객체 (예: 여러 행, 문서 또는 여러 테이블/컬렉션)

---

# Single-Object

# 단일 객체

- The transaction involves operations on a single database object (like one row in a relational table or one document in a NoSQL database).
- This type of transaction is simpler and often requires fewer resources to ensure **atomicity** and **isolation** since only one object is affected.

- 트랜잭션은 단일 데이터베이스 객체(관계형 테이블의 하나의 행 또는 NoSQL 데이터베이스의 하나의 문서 등)에 대한 연산을 포함한다.
- 이러한 유형의 트랜잭션은 하나의 객체에만 영향을 미치기 때문에 **원자성(atomicity)**과 **격리성(isolation)**을 보장하는 데 필요한 리소스가 더 적고 비교적 단순하다.

---

# Characteristics of Single-Object Transactions

# 단일 객체 트랜잭션의 특징

- **Simplicity:** Single-object transactions are often lightweight and simple to implement since they don’t involve complex locking or consistency mechanisms across multiple objects.
- **Performance:** Since only one object is affected, these transactions are typically fast and have minimal impact on database performance.
- **Isolation and Locking:** With single-object operations, isolation can often be achieved using basic locking mechanisms at the row or document level. This prevents other transactions from modifying the object while the transaction is ongoing.

- **단순성(Simplicity):** 단일 객체 트랜잭션은 여러 객체에 걸친 복잡한 잠금이나 일관성 메커니즘을 포함하지 않기 때문에 대체로 가볍고 구현하기 쉽다.
- **성능(Performance):** 하나의 객체에만 영향을 미치므로 이러한 트랜잭션은 일반적으로 빠르며 데이터베이스 성능에 미치는 영향이 적다.
- **격리성과 잠금(Isolation and Locking):** 단일 객체 연산에서는 행 또는 문서 수준의 기본적인 잠금 메커니즘을 사용하여 격리성을 구현할 수 있다. 이를 통해 트랜잭션이 진행되는 동안 다른 트랜잭션이 해당 객체를 수정하는 것을 방지한다.

---

# Example. Single-Object

# 예시. 단일 객체

- Consider a shopping cart application where a customer wants to update the quantity of a single item in their cart. The transaction involves:
  - Retrieving the item’s current quantity.
  - Updating the quantity to the desired number.
- **This operation impacts only one row (or document) in the database**, making it a single-object transaction. It’s straightforward because only one item needs to be read and modified.

- 고객이 장바구니에 있는 하나의 상품 수량을 변경하려는 쇼핑 카트 애플리케이션을 생각해보자. 트랜잭션에는 다음 작업이 포함된다.
  - 상품의 현재 수량을 조회한다.
  - 수량을 원하는 값으로 변경한다.
- **이 연산은 데이터베이스의 하나의 행(또는 문서)에만 영향을 미치므로** 단일 객체 트랜잭션에 해당한다. 하나의 항목만 읽고 수정하면 되기 때문에 간단하다.

---

# Multi-Object

# 다중 객체

- A multi-object transaction involves operations on multiple objects (e.g., multiple rows in the same table, rows in different tables, or documents in different collections).
- Multi-object transactions are more complex because they require consistency and coordination across all affected objects.
- Example
  - Funds Transfer Between Bank Accounts
  - E-commerce Order Processing(Order & Inventory)
  - Inventory Management in Warehouses(Locations)

- 다중 객체 트랜잭션은 여러 객체에 대한 연산을 포함한다(예: 동일한 테이블의 여러 행, 서로 다른 테이블의 행 또는 서로 다른 컬렉션의 문서).
- 다중 객체 트랜잭션은 영향을 받는 모든 객체에 걸쳐 일관성과 조정이 필요하기 때문에 더 복잡하다.
- 예시
  - 은행 계좌 간 자금 이체
  - 전자상거래 주문 처리(주문 & 재고)
  - 창고의 재고 관리(위치)

---

# Characteristics of Multi-Object Transactions

# 다중 객체 트랜잭션의 특징

- **Complexity:** Multi-object transactions involve more complex mechanisms to ensure that the operations across multiple objects are completed together. This often requires additional locking, more sophisticated isolation levels, and careful handling of rollbacks.
- **Performance Overhead:** Since multi-object transactions lock multiple resources, they can impact database performance, especially in high-concurrency environments. Managing dependencies between objects can also introduce overhead.
- **Consistency and Isolation:** Maintaining consistency across multiple objects is challenging. More robust isolation levels (e.g., serializability) may be needed to prevent other transactions from interfering with any of the involved objects.

- **복잡성(Complexity):** 다중 객체 트랜잭션은 여러 객체에 대한 연산이 함께 완료되도록 보장하기 위해 더 복잡한 메커니즘을 사용한다. 이를 위해 추가적인 잠금, 더 정교한 격리 수준, 그리고 세심한 롤백 처리가 필요한 경우가 많다.
- **성능 오버헤드(Performance Overhead):** 다중 객체 트랜잭션은 여러 리소스를 잠그기 때문에 특히 동시성이 높은 환경에서 데이터베이스 성능에 영향을 줄 수 있다. 객체 간의 의존성을 관리하는 것 역시 추가적인 오버헤드를 발생시킬 수 있다.
- **일관성과 격리성(Consistency and Isolation):** 여러 객체에 걸쳐 일관성을 유지하는 것은 어렵다. 다른 트랜잭션이 관련된 객체에 간섭하는 것을 방지하기 위해 더 강력한 격리 수준(예: 직렬화 가능성, serializability)이 필요할 수 있다.

---

# Example. Multi-Object

# 예시. 다중 객체

- Consider a banking application where a customer wants to transfer money from one account to another. This transaction involves:
  - Deducting the amount from Account A.
  - Adding the same amount to Account B.
- In this case, **two rows (or records) in the database need to be updated atomically to maintain consistency.**
- This is a multi-object transaction since it affects both Account A and Account B. If either the deduction or addition operation fails, the entire transaction must be rolled back to ensure that neither account’s balance is left in an incorrect state.

- 고객이 한 계좌에서 다른 계좌로 돈을 이체하려는 은행 애플리케이션을 생각해보자. 이 트랜잭션에는 다음 작업이 포함된다.
  - 계좌 A에서 금액을 차감한다.
  - 동일한 금액을 계좌 B에 추가한다.
- 이 경우 **일관성을 유지하기 위해 데이터베이스의 두 행(또는 레코드)을 원자적으로 업데이트해야 한다.**
- 계좌 A와 계좌 B 모두에 영향을 미치므로 다중 객체 트랜잭션이다. 금액 차감이나 추가 작업 중 하나라도 실패하면 어느 계좌의 잔액도 잘못된 상태로 남지 않도록 전체 트랜잭션을 롤백해야 한다.

# Key Points of Comparison

# 주요 비교 사항

| Aspect | Single-Object Transaction | Multi-Object Transaction |
| --- | --- | --- |
| Complexity | Simple and requires basic transaction management | More complex with higher risk of concurrency issues |
| Performance | Typically faster and less resource-intensive | Can slow down due to locking and coordination efforts |
| Consistency | Easier to maintain consistency on a single object | Requires careful handling to maintain consistency |
| Isolation | Basic locking mechanisms are usually sufficient | Advanced isolation levels may be required |

| 항목 | 단일 객체 트랜잭션 | 다중 객체 트랜잭션 |
| --- | --- | --- |
| 복잡성 | 단순하며 기본적인 트랜잭션 관리가 필요함 | 더 복잡하며 동시성 문제가 발생할 위험이 더 높음 |
| 성능 | 일반적으로 더 빠르고 적은 리소스를 사용함 | 잠금과 조정 작업으로 인해 느려질 수 있음 |
| 일관성 | 단일 객체의 일관성을 유지하기가 더 쉬움 | 일관성을 유지하기 위해 세심한 처리가 필요함 |
| 격리성 | 일반적으로 기본적인 잠금 메커니즘으로 충분함 | 고급 격리 수준이 필요할 수 있음 |

# Error and Abort Handling

# 오류 및 중단 처리

| Aspect | Single-Object Transaction | Multi-Object Transaction |
| --- | --- | --- |
| Error Detection | Basic validation, easy to catch issues early | Requires validation across multiple objects |
| Error Logging | Log simple errors | Log critical errors with alerts |
| Rollback | Simple rollback, single object | Rollback all changes across objects |
| Retry Mechanism | Lightweight retry, generally safe | Use cautiously, prefer idempotent transactions |
| Automatic Aborts | Often automatic for single-object errors | Requires coordinated rollback for multi-object aborts |

| 항목 | 단일 객체 트랜잭션 | 다중 객체 트랜잭션 |
| --- | --- | --- |
| 오류 감지 | 기본적인 검증으로 문제를 조기에 발견하기 쉬움 | 여러 객체에 걸친 검증이 필요함 |
| 오류 로깅 | 단순한 오류를 기록함 | 중요한 오류를 알림과 함께 기록함 |
| 롤백 | 단일 객체에 대한 단순한 롤백 | 여러 객체에 걸친 모든 변경 사항을 롤백함 |
| 재시도 메커니즘 | 가벼운 재시도로 일반적으로 안전함 | 신중하게 사용해야 하며 멱등성을 가진 트랜잭션을 권장함 |
| 자동 중단 | 단일 객체 오류의 경우 자동으로 처리되는 경우가 많음 | 다중 객체 중단의 경우 조정된 롤백이 필요함 |
