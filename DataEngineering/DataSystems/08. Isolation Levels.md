# Weak Isolation Levels in Transaction

# 트랜잭션의 약한 격리 수준

---

# What is Isolation level?

# 격리 수준이란 무엇인가?

- In database transactions, **isolation levels define the degree to which the operations of a transaction are isolated from the operations of other concurrent transactions.**
- Weak Isolation Levels
  - **Read Uncommitted**
  - **Read Committed**
  - **Repeatable Read**

- 데이터베이스 트랜잭션에서 **격리 수준(isolation level)은 한 트랜잭션의 연산이 동시에 실행되는 다른 트랜잭션의 연산으로부터 어느 정도 격리되는지를 정의한다.**
- 약한 격리 수준
  - **Read Uncommitted**
  - **Read Committed**
  - **Repeatable Read**

---

# Read Uncommitted

# Read Uncommitted

- The weakest isolation level.
- Transactions can see uncommitted changes made by other transactions, which might later be rolled back.
- Anomalies
  - **Dirty Reads:** Reading data that has been written by a transaction but not yet committed.
  - **Non-Repeatable Reads** and **Phantom Reads** can also occur.
- Use Case: Situations where accuracy is less critical than **performance**, such as certain reporting systems or logging.

- 가장 약한 격리 수준이다.
- 트랜잭션은 다른 트랜잭션이 변경했지만 아직 커밋하지 않은 데이터를 볼 수 있으며, 해당 변경 사항은 이후 롤백될 수도 있다.
- 이상 현상
  - **Dirty Reads:** 다른 트랜잭션이 작성했지만 아직 커밋하지 않은 데이터를 읽는 현상이다.
  - **Non-Repeatable Reads**와 **Phantom Reads**도 발생할 수 있다.
- 사용 사례: 일부 리포팅 시스템이나 로깅처럼 정확성보다 **성능**이 더 중요한 상황에서 사용된다.

```sql
UPDATE seat_assignment SET booked=1 WHERE seat_id='10a' AND time='2024-11-01T02:15'

Select * FROM seat_assignment WHERE time='2024-11-01T02:15'
```


# Read Committed
= Read Uncommitted보다 조금 더 강한 격리 수준이다.
- **Dirty Read가 발생하지 않는다.**
    - Read Committed 격리 수준에서는 **트랜잭션이 다른 트랜잭션에 의해 커밋된 데이터만 읽는다.**
    - Dirty Read는 다른 트랜잭션이 작성했지만 아직 커밋하지 않은 데이터를 읽을 때 발생한다. Read Committed는 읽는 데이터가 안정적이고 커밋된 데이터임을 보장하여 이를 방지한다.
- **Dirty Write가 발생하지 않는다.**
    - Dirty Write는 **한 트랜잭션이 아직 커밋되지 않은 다른 트랜잭션이 작성한 데이터를 덮어쓸 때 발생한다.**
    - Read Committed는 트랜잭션이 수정하는 데이터에 대해 배타적 쓰기 잠금을 획득하도록 하여 Dirty Write를 방지한다. 이를 통해 아직 커밋되지 않은 다른 트랜잭션이 동시에 동일한 데이터에 쓰는 것을 방지한다.

- 일반적으로 **잠금 메커니즘(locking mechanisms)**을 사용하여 구현한다.
    - Read Locks (Shared Locks): Dirty Read를 방지하기 위해 데이터를 읽을 때 획득한다.
    - Write Locks (Exclusive Locks): Dirty Write를 방지하기 위해 데이터를 쓸 때 획득한다.
- 잠금은 전체 트랜잭션 동안 유지되는 것이 아니라 해당 연산이 수행되는 동안만 유지되므로 성능을 향상시킨다.
- 이상 현상
    - Non-Repeatable Reads: 동일한 트랜잭션에서 데이터를 다시 읽을 경우 값이 변경되어 있을 수 있다.
    - Phantom Reads: 현재 트랜잭션이 실행되는 도중 다른 트랜잭션에 의해 새로운 행이 추가되는 현상이 여전히 발생할 수 있다.

Repeatable Read
- 트랜잭션이 데이터를 읽으면 해당 트랜잭션이 진행되는 동안 그 데이터가 변경되지 않도록 보장한다.
- Snapshot Isolation 구현
    - Snapshot Isolation(SI)은 특정 시점의 데이터베이스에 대한 일관된 스냅샷을 트랜잭션에 제공한다.
- **Multi-Version Concurrency Control (MVCC)**을 사용하여 구현한다.
    - 각 쓰기 연산은 기존 버전을 덮어쓰지 않고 새로운 데이터 버전을 생성한다.
    - 읽기 작업은 트랜잭션이 시작된 시점에 가장 최신이었던 데이터 버전에 접근한다.

Repeatable Read
- 일관된 스냅샷을 관찰하기 위한 가시성 규칙
    - 트랜잭션은 다음 데이터를 볼 수 있다.
        - 트랜잭션이 시작되기 전에 커밋된 모든 데이터
        - 트랜잭션이 시작된 후 커밋된 다른 트랜잭션의 변경 사항은 볼 수 없음
    - 이를 통해 트랜잭션이 실행되는 동안 데이터의 일관성이 유지된다.

- 인덱스와 Snapshot Isolation
    - 일관성을 유지하려면 인덱스를 신중하게 관리해야 한다.
        - 인덱스 엔트리도 해당 인덱스가 참조하는 데이터와 함께 버전 관리된다.
        - 인덱스를 사용하는 쿼리는 해당 트랜잭션의 스냅샷에서 볼 수 있는 데이터 버전을 조회한다.

# Repeatable Read

# 반복 가능한 읽기

- Anomalies
  - **Phantom Reads:** New rows added by other transactions can still appear when a range of records is queried.
- Use Case: Scenarios requiring a high level of consistency but where it's acceptable if new rows appear during range queries, like some financial applications.

- 이상 현상
  - **Phantom Reads:** 일정 범위의 레코드를 조회할 때 다른 트랜잭션이 추가한 새로운 행이 나타날 수 있다.
- 사용 사례: 높은 수준의 일관성이 필요하지만, 일부 금융 애플리케이션처럼 범위 쿼리 중 새로운 행이 나타나는 것은 허용할 수 있는 상황에서 사용된다.

# Avoid Lost Updates

# 갱신 손실 방지

- **Atomic Write Operations**
  - Atomicity ensures that **a series of operations within a transaction** are completed entirely or not at all.
  - Atomic write operations prevent lost updates by ensuring that concurrent transactions do not partially overwrite each other's changes.
- **Explicit Locking**
  - Developers can use explicit locks to control concurrency:
    - Pessimistic Locking: Locks data when it is read to prevent other transactions from modifying it.
    - Commands like **SELECT FOR UPDATE** lock the selected rows until the transaction completes.

- **원자적 쓰기 연산(Atomic Write Operations)**
  - 원자성은 **트랜잭션 내의 일련의 연산**이 모두 완료되거나 전혀 수행되지 않도록 보장한다.
  - 원자적 쓰기 연산은 동시에 실행되는 트랜잭션들이 서로의 변경 사항을 부분적으로 덮어쓰지 않도록 보장하여 갱신 손실을 방지한다.
- **명시적 잠금(Explicit Locking)**
  - 개발자는 명시적 잠금을 사용하여 동시성을 제어할 수 있다.
    - 비관적 잠금(Pessimistic Locking): 데이터를 읽을 때 잠금을 설정하여 다른 트랜잭션이 해당 데이터를 수정하지 못하도록 한다.
    - **SELECT FOR UPDATE**와 같은 명령은 트랜잭션이 완료될 때까지 선택된 행을 잠근다.

Write Skew and Phantoms
쓰기 스큐와 팬텀
- 쓰기 스큐의 특징(Characterizing Write Skew)
    - 쓰기 스큐(Write Skew)는 동시에 실행되는 두 트랜잭션이 서로 겹치는 데이터를 읽은 후 해당 데이터를 기반으로 결정을 내리면서 일관되지 않은 결과가 발생하는 현상이다.
    - 각 트랜잭션은 데이터를 읽는 시점에는 유효한 상태를 볼 수 있지만, 다른 트랜잭션의 작업과 결합되면 해당 상태가 유효하지 않게 될 수 있다.

- 쓰기 스큐의 예시

        - 두 사람 모두 휴가를 사용하기로 결정하여 해당 자리에 근무자가 없는 상태가 된다.
    - 은행 계좌 예시
        - 두 트랜잭션이 최소 준비금을 유지하는지 확인하기 위해 잔액을 확인한다.
        - 두 트랜잭션 모두 상대방의 아직 처리 중인 트랜잭션을 보지 못한 채 자금을 인출하여 전체 잔액이 필요한 최소 준비금 아래로 떨어지게 된다.

# What is Serializability?

# 직렬화 가능성이란 무엇인가?

- It defines a condition where **the result of executing a set of transactions concurrently is equivalent to executing them in some serial order.**
- Concurrency control mechanisms
  - Actual Serial Execution
  - Two-Phase Locking (2PL)
  - Serializable Snapshot Isolation (SSI)

- **여러 트랜잭션을 동시에 실행한 결과가 해당 트랜잭션들을 어떤 순차적인 순서로 실행한 결과와 동일한 상태**를 의미한다.
- 동시성 제어 메커니즘
  - 실제 순차 실행(Actual Serial Execution)
  - 2단계 잠금(Two-Phase Locking, 2PL)
  - 직렬화 가능 스냅샷 격리(Serializable Snapshot Isolation, SSI)

---

# Actual Serial Execution

# 실제 순차 실행

- Actual serial execution means **executing transactions one at a time**, in a sequential (serial) order, without overlapping.
- **Characteristics**
  - Transactions are executed strictly one after another.
  - Guarantees serializability, the strongest level of consistency, because no two transactions interfere with each other.
  - No need for concurrency control mechanisms, as there’s no parallelism.

- 실제 순차 실행은 트랜잭션들이 서로 겹치지 않도록 **한 번에 하나씩** 순차적인 순서로 실행하는 것을 의미한다.
- **특징(Characteristics)**
  - 트랜잭션은 엄격하게 하나씩 차례대로 실행된다.
  - 두 트랜잭션이 서로 간섭하지 않기 때문에 가장 강력한 수준의 일관성인 직렬화 가능성을 보장한다.
  - 병렬 처리가 없기 때문에 동시성 제어 메커니즘이 필요하지 않다.

---

# Actual Serial Execution

# 실제 순차 실행

- **Pros**
  - **Simplest way** to ensure correctness and avoid issues like dirty reads, lost updates, and write skew.
- **Cons**
  - **Extremely poor performance and scalability** because it doesn’t exploit parallelism or concurrent execution.
- Usage: Rarely used in practice due to its inefficiency; often serves as a baseline or theoretical model to define correctness (serializability).

- **장점(Pros)**
  - 정확성을 보장하고 Dirty Read, Lost Update, Write Skew와 같은 문제를 방지하는 **가장 단순한 방법**이다.
- **단점(Cons)**
  - 병렬 처리나 동시 실행을 활용하지 않기 때문에 **성능과 확장성이 매우 낮다.**
- 사용: 비효율적이기 때문에 실제 환경에서는 거의 사용되지 않으며, 정확성(직렬화 가능성)을 정의하기 위한 기준이나 이론적 모델로 주로 사용된다.

# Two-Phase Locking (2PL)

# 2단계 잠금 (2PL)

- A concurrency control protocol that **ensures serializability by dividing the locking process into two distinct phases.**
  - **Growing phase:** A transaction acquires locks but cannot release any lock.
  - **Shrinking phase:** A transaction releases locks but cannot acquire any new lock.
- Lock Types
  - **Shared Lock (S-Lock)**
    - Used for read operations.
    - Multiple transactions can hold a shared lock on the same data item simultaneously.
  - **Exclusive Lock (X-Lock)**
    - Used for write operations.
    - **Only one transaction can hold an exclusive lock on a data item**, and no other transaction can hold a shared or exclusive lock on the same item.

- 잠금 과정을 **두 개의 서로 다른 단계로 나누어 직렬화 가능성을 보장하는 동시성 제어 프로토콜**이다.
  - **확장 단계(Growing phase):** 트랜잭션은 잠금을 획득할 수 있지만 어떠한 잠금도 해제할 수 없다.
  - **축소 단계(Shrinking phase):** 트랜잭션은 잠금을 해제할 수 있지만 새로운 잠금을 획득할 수 없다.
- 잠금 유형
  - **공유 잠금(Shared Lock, S-Lock)**
    - 읽기 연산에 사용된다.
    - 여러 트랜잭션이 동일한 데이터 항목에 대해 동시에 공유 잠금을 가질 수 있다.
  - **배타적 잠금(Exclusive Lock, X-Lock)**
    - 쓰기 연산에 사용된다.
    - **하나의 데이터 항목에 대해 하나의 트랜잭션만 배타적 잠금을 가질 수 있으며**, 다른 트랜잭션은 동일한 항목에 공유 잠금이나 배타적 잠금을 가질 수 없다.

# Two-Phase Locking (2PL)

# 2단계 잠금 (2PL)

- Transactions
  - T1: Reads X, Write X
  - T2: Reads X, Write X
- Without 2PL
  - T1: Reads X
  - T2: Reads X
  - T1: Writes X
  - T2: Writes X
- Outcome
  - T2 overwrites T1’s changes, leading to **lost updates.**

- 트랜잭션
  - T1: X를 읽고, X에 쓴다.
  - T2: X를 읽고, X에 쓴다.
- 2PL을 사용하지 않는 경우
  - T1: X를 읽는다.
  - T2: X를 읽는다.
  - T1: X에 쓴다.
  - T2: X에 쓴다.
- 결과
  - T2가 T1의 변경 사항을 덮어쓰면서 **Lost Update(갱신 손실)**가 발생한다.

# Two-Phase Locking (2PL)

# 2단계 잠금 (2PL)

- With 2PL
  - T1: Acquires S-Lock on X (growing phase).
  - T1: Reads X.
  - T1: Requests X-Lock on X (still growing phase).
  - T1: Writes X.
  - T1: Releases X-Lock on X (shrinking phase).
  - T2: Acquires S-Lock on X (starts after T1 finishes).
- Outcome
  - Serializability is maintained.

- 2PL을 사용하는 경우
  - T1: X에 대한 S-Lock을 획득한다(확장 단계).
  - T1: X를 읽는다.
  - T1: X에 대한 X-Lock을 요청한다(여전히 확장 단계).
  - T1: X에 쓴다.
  - T1: X에 대한 X-Lock을 해제한다(축소 단계).
  - T2: X에 대한 S-Lock을 획득한다(T1이 완료된 후 시작).
- 결과
  - 직렬화 가능성이 유지된다.


  # Two-Phase Locking (2PL)

# 2단계 잠금 (2PL)

- Deadlock in 2PL
  - T1: Acquires X-Lock on A.
  - T2: Acquires X-Lock on B.
  - T1: Requests X-Lock on B (waiting for T2).
  - T2: Requests X-Lock on A (waiting for T1).
  - This creates a circular dependency, leading to a deadlock.
- Deadlock Resolution
  - **Timeouts:** Abort transactions that have been waiting for too long.
  - **Wait-Die or Wound-Wait:** Use timestamps to decide which transaction should abort.
  - **Deadlock Detection:** Periodically check for cycles in the wait-for graph and abort transactions to break the cycle.

- 2PL에서의 데드락
  - T1: A에 대한 X-Lock을 획득한다.
  - T2: B에 대한 X-Lock을 획득한다.
  - T1: B에 대한 X-Lock을 요청한다(T2를 기다림).
  - T2: A에 대한 X-Lock을 요청한다(T1을 기다림).
  - 이로 인해 순환 의존성이 생성되어 데드락이 발생한다.
- 데드락 해결
  - **Timeouts:** 너무 오랫동안 대기한 트랜잭션을 중단한다.
  - **Wait-Die or Wound-Wait:** 타임스탬프를 사용하여 어떤 트랜잭션을 중단할지 결정한다.
  - **Deadlock Detection:** Wait-for 그래프에서 주기적으로 사이클이 존재하는지 확인하고, 사이클을 끊기 위해 트랜잭션을 중단한다.

# Two-Phase Locking (2PL)

# 2단계 잠금 (2PL)

- **Pros**
  - Guarantees serializability.
  - Strict and rigorous variants make recovery easier in case of failure.
- **Cons**
  - Can lead to **deadlocks**, where two or more transactions wait indefinitely for each other’s locks.
  - May reduce concurrency due to long lock durations.
- **Usage**
  - Widely used in traditional relational databases like MySQL (InnoDB) and SQL Server for transaction isolation.

- **장점(Pros)**
  - 직렬화 가능성을 보장한다.
  - Strict 및 Rigorous 방식의 변형은 장애 발생 시 복구를 더 쉽게 만든다.
- **단점(Cons)**
  - 두 개 이상의 트랜잭션이 서로의 잠금을 무한히 기다리는 **데드락(deadlock)**이 발생할 수 있다.
  - 잠금이 오랫동안 유지되기 때문에 동시성이 감소할 수 있다.
- **사용(Usage)**
  - 트랜잭션 격리를 위해 MySQL(InnoDB), SQL Server와 같은 전통적인 관계형 데이터베이스에서 널리 사용된다.

# Serializable Snapshot Isolation (SSI)

# 직렬화 가능 스냅샷 격리 (SSI)

- An advanced isolation level that **combines snapshot isolation (SI) with mechanisms to ensure serializability.**
- **Snapshot Isolation (SI)**
  - Transactions read from a consistent snapshot of the database as of their start time.
  - Prevents issues like dirty reads and non-repeatable reads.
  - However, SI by itself is not serializable and may allow anomalies like write skew.
- **SSI Mechanism**
  - Detects and prevents anomalies that would violate serializability.
  - **Tracks dependencies between concurrent transactions** and aborts transactions that might cause inconsistencies.
  - Example: If two concurrent transactions modify overlapping data in ways that would break serializability, one of them is rolled back.

- **스냅샷 격리(SI)와 직렬화 가능성을 보장하기 위한 메커니즘을 결합한** 고급 격리 수준이다.
- **스냅샷 격리(Snapshot Isolation, SI)**
  - 트랜잭션은 시작 시점을 기준으로 데이터베이스의 일관된 스냅샷에서 데이터를 읽는다.
  - Dirty Read와 Non-Repeatable Read와 같은 문제를 방지한다.
  - 하지만 SI 자체만으로는 직렬화 가능성을 보장하지 않으며 Write Skew와 같은 이상 현상이 발생할 수 있다.
- **SSI 메커니즘**
  - 직렬화 가능성을 위반할 수 있는 이상 현상을 감지하고 방지한다.
  - **동시에 실행되는 트랜잭션 간의 의존성을 추적**하고 일관성 문제를 발생시킬 수 있는 트랜잭션을 중단한다.
  - 예시: 동시에 실행되는 두 트랜잭션이 서로 겹치는 데이터를 직렬화 가능성을 깨뜨리는 방식으로 수정하면 둘 중 하나를 롤백한다.

# Serializable Snapshot Isolation (SSI)

# 직렬화 가능 스냅샷 격리 (SSI)

- **Read-Write Conflicts**
  - Occur when a transaction T1 reads a value written by another transaction T2, and T2 later commits.
  - SSI ensures that these conflicts are tracked and checked for serializability.
- **Write-Write Conflicts**
  - Occur when two transactions write to the same data item.
  - These conflicts are inherently avoided in SI, but SSI tracks them to build the dependency graph.
- **Write Skew**
  - A specific type of anomaly where two transactions read overlapping data and update disjoint parts based on their reads.
  - SSI detects this by identifying dependencies between the transactions and aborting one if needed.

- **읽기-쓰기 충돌(Read-Write Conflicts)**
  - 트랜잭션 T1이 다른 트랜잭션 T2가 작성한 값을 읽고 이후 T2가 커밋할 때 발생한다.
  - SSI는 이러한 충돌을 추적하고 직렬화 가능성을 만족하는지 확인한다.
- **쓰기-쓰기 충돌(Write-Write Conflicts)**
  - 두 트랜잭션이 동일한 데이터 항목에 쓰기 작업을 수행할 때 발생한다.
  - 이러한 충돌은 SI에서 본질적으로 방지되지만, SSI는 의존성 그래프를 구성하기 위해 이를 추적한다.
- **쓰기 스큐(Write Skew)**
  - 두 트랜잭션이 서로 겹치는 데이터를 읽은 뒤, 읽은 결과를 기반으로 서로 다른 부분을 업데이트할 때 발생하는 특정 유형의 이상 현상이다.
  - SSI는 트랜잭션 간 의존성을 식별하고 필요한 경우 하나의 트랜잭션을 중단하여 이를 감지한다.

# Serializable Snapshot Isolation (SSI)

# 직렬화 가능 스냅샷 격리 (SSI)

- **Pros**
  - **Maintains high concurrency** by allowing transactions to proceed in parallel without locking.
  - Provides serializable isolation with better performance than strict locking protocols.
- **Cons**
  - May result in **more frequent transaction aborts**, especially under high contention.
  - More complex to implement than 2PL.
- Usage: Used in modern databases like PostgreSQL and FoundationDB, which provide serializable isolation without relying on traditional locking mechanisms.

- **장점(Pros)**
  - 트랜잭션이 잠금 없이 병렬로 진행될 수 있도록 하여 **높은 동시성을 유지한다.**
  - 엄격한 잠금 프로토콜보다 더 나은 성능으로 직렬화 가능한 격리를 제공한다.
- **단점(Cons)**
  - 특히 경합이 심한 상황에서는 **트랜잭션 중단이 더 자주 발생할 수 있다.**
  - 2PL보다 구현이 더 복잡하다.
- 사용: 전통적인 잠금 메커니즘에 의존하지 않고 직렬화 가능한 격리를 제공하는 PostgreSQL, FoundationDB와 같은 현대적인 데이터베이스에서 사용된다.
