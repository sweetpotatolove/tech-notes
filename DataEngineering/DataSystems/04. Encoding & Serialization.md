# Encoding & Serialization
## Encoding / Decoding (SerDe) to Evolve 인코딩/디코딩의 진화?
### 데이터의 진화 (Evolvability)
- 데이터 모델이 바뀌는 것 (Things can change)
    - 관계형 데이터베이스의 데이터 모델: `ALTER TABLE`
        - 필드 추가, 삭제, 변경 될 수 있음
    - 변경된 스키마를 읽어들이기 위해서는 애플리케이션 코드도 함께 변경되어야 함

- 때문에 새 버전 코드와 기존 버전 코드가 공존하게 됨
    - 서비스 중단(Downtime)을 방지하기 위해 서버는 롤링 업그레이드를 수행
        - rolling upgrade: 서버를 한대씩 업그레이드?
    - 클라이언트의 업그레이드는 서버가 통제할 수 없음
        - ex. 클라이언트가 라이브러리를 업데이트 하지 않는 경우

- 호환성(Compatibility)
    - 하위 호환성(Backward Compatibility): 새로운 버전이 이전 버전에서 작성한 데이터를 읽을 수 있어야 함
    - 상위 호환성(Forward Compatibility): 이전 버전이 새로운 버전에서 작성한 데이터를 읽을 수 있어야 함

### 인코딩 형식(Encoding Formats)
- 메모리 내부(In-memory)
    - 포인터를 사용하는 객체(Object), 구조체(Struct), 리스트(List), 트리(Tree), 해시 테이블(Hash Table) 등의 자료구조
    - 이를 디스크에 저장하거나 네트워크로 전송하기 위해 바이트(Byte) 형태로 변환해야 함 = 인코딩

- 인코딩(Encoding)
    - 메모리 구조를 바이트 배열(Byte Array)로 변환하는 과정
    - ex. Serialization(직렬화), Marshaling

- 디코딩(Decoding): 바이트 배열을 메모리 구조로 변환하는 과정
    - ex. Deserialization(역직렬화), Unmarshalling

- 인코딩 형식의 요구사항
    - ① 프로그래밍 언어에 독립적이어야 한다.
        - Java의 `java.io.Serializable`, Python의 `pickle`, Ruby의 `Marshal`에 의존할 필요가 없어야 함
    - ② 보안성이 확보되어야 한다.
        - 객체를 직접 생성(Invocation)하는 방식은 위험할 수 있음
    - ③ 버전 관리(Versioning)를 지원해야 한다.
        - 하위 호환성과 상위 호환성을 지원해야 함
    - ④ 효율적이고 데이터 크기가 작아야 한다.
    - ①, ④에 위반되기 때문에? `java.io.Serializable`, `pickle`, `Marshal`를 범용적인 인코딩에 사용하는 것을 추천하지 않음

### 인코딩 형식 ① - 텍스트 형식(Text Format)
- 형식(Formats)
    - `XML` : 표현이 장황하고 복잡함
        - 태그가 양쪽에 붙어있고, 괄호가 많아서 복잡하고 김
    - `JSON` : 웹 브라우저에서 기본적으로 지원하며 XML보다 단순
    - `CSV` : 단순한 테이블 형태의 데이터 형식이다.

- 단점
    - 타입 정보가 없음
        - 문자열과 숫자를 구분하지 못하며, 부동소수점의 정밀도를 보장하지 않음
        - JSON은 따옴표를 이용해 문자, 숫자를 구분하지만 부동소수점 정확하게 표현 못함
    - 사람이 읽을 수 있는 문자만 표현할 수 있으며, Base64만으로는 충분하지 않음
        - 바이너리 데이터는 텍스트로 표현할 수 있지만 Base64와 같은 다른 인코딩을 사용해야만 함
        - 근데 Base64가 효율성이 떨어짐
    - 스키마를 지원하기 까다로움

### 인코딩 형식 ② - 바이너리 형식(Binary Format)
- 타입 정보 문제를 해결하기 위해 바이너리 형식을 사용
    - Binary JSON, Binary XML
    - 하지만 데이터의 장황함(Verbosity)을 완전히 해결하거나 저장 공간을 크게 절약하지는 못함
        - 불필요한 태그가 붙어다닌 다던지.. 하는 불편함을 해소시킬 순 없음

- MessagePack 예시

    ```json
    {"string": "value", "number": 4887, "list": ["element1", "element2"]}
    ```

    - 위 JSON을 바이터리 형식으로 표현

        - 필드 이름(string, number ..)들이 JSON 포맷에 들어가있는 것처럼 바이너리 형태에서도 불필요하게 들어가있음
        - 그러나 숫자들이 바이너리 형태로 표현되어 있고 따옴표가 없는건 장점?

### 인코딩 형식 ③ - ProtoBuf와 Thrift
- Google과 Facebook에서 개발됨
- 다양한 프로그래밍 언어의 코드 생성(Code Generation) 도구를 함께 제공함

    - protobuf 스키마 예제

        ```protobuf
        message Example {
            required string string_field = 1;
            optional int64 number_field = 2;
            repeated string str_array_field = 3;
        }
        ```
        - 스키마를 지정하면 스키마대로 데이터를 씀(인코딩)
        - 읽고 디코딩할 수 있는 코드를 생성?
    
    - thrift 스키마 예제

        ```thrift
        struct Example {
            1: required string stringField,
            2: optional i64 numberField,
            3: optional list<string> strArrayField
        }
        ```

- 가변 바이트 인코딩(Variable Byte Encoding) - Variant
    - 간단한 정수 압축 방식으로, 작은 숫자를 저장할 때 매우 효율적
    - 바이트 단위로 정수를 표현하는데, 7비트 단위로 정수를 저장하며, 최상위 비트(MSB)를 연속 비트(Continuation Bit)로 사용함
        - MSB가 1이면 다음 바이트가 계속 이어지고, 0이면 마지막 바이트를 의미
        - `0~127`: 1바이트, `128~16383`: 2바이트로 저장됨
        - 그래서 작은 정수를 4, 8 byte 모두 사용하지 않고 1, 2 byte만 사용해서 표현 가능
    - 단조 증가(Monotonically Increasing)하는 수열을 저장할 때 매우 효율적
        - 단조 증가: 현재 숫자와 그 다음 숫자와의 차이가 작음? 
        - 검색 엔진의 인덱스(Index), Posting Array 등에 사용됨

- ProtoBuf 형식 - Protocol Buffers 공식 문서

    ```ProtoBuf
    message      := (tag value)*

    tag          := (field << 3) bit-or wire_type;
                    encoded as uint32 varint

    value        := varint        for wire_type == VARINT,
                    i32           for wire_type == I32,
                    i64           for wire_type == I64,
                    len-prefix    for wire_type == LEN,
                    <empty>       for wire_type == SGROUP or EGROUP

    varint       := int32 | int64 | uint32 | uint64 | bool | enum | sint32 | sint64;
                    encoded as varints (sintN are ZigZag-encoded first)

    i32          := sfixed32 | fixed32 | float;
                    encoded as 4-byte little-endian;
                    memcpy of the equivalent C types (uint32_t, float)

    i64          := sfixed64 | fixed64 | double;
                    encoded as 8-byte little-endian;
                    memcpy of the equivalent C types (uint64_t, double)

    len-prefix   := size (message | string | bytes | packed);
                    size encoded as int32 varint

    string       := valid UTF-8 string (e.g. ASCII);
                    max 2GB of bytes

    bytes        := any sequence of 8-bit bytes;
                    max 2GB of bytes

    packed       := varint* | i32* | i64*,
                    consecutive values of the type specified in `.proto`
    ```
    - message는 tag와 value의 연속
    - tag는 field id를? 3bit shift한 값과 wire type를 표현한 숫자에 bit 와이즈 or 한 값?
    - wire type은 varint, 32bit 숫자, 64bit 숫자, .. 5가지만 있기 때문에 3bit만 쓰면 된다?
    - 문자열은 길이를 쓰고(len-prefix), UTF-8로 byte를 나열하면 됨
    - 즉, 스키마에서 정의한 필드들을 tag 벨류에 연속된 바이트 시퀀스로 써내려가는 방식

- Thrift 형식
    - 두 가지 형식이 있음
        - BinaryProtocol
        - CompactProtocol
    - 두 형식은 문법적으로 동일하지만, CompactProtocol은 가변 바이트 인코딩을 사용함
        - 그래서 사이즈가 작다?

- ProtoBuf/Thrift의 스키마 진화
    - 필드 이름 대신 태그를 사용
    - 필수 데이터를 런타임에 검사하기 위해 required 필드를 사용
        - 런타임 검사 시 값이 없으면 에러를 일으키도록 필수 데이터에는 required 키워드를 붙일 수 있음
    - 새로운 태그를 부여하고 optional로 새 필드를 추가
        - 새로운 필드 추가 시 optional로 새 태그 붙여놓음?
        - 그럼 하위 호환성과 상위 호환성을 충족시킬 수 있음
        - 새롭게 추가된 필드는 이전에 코드가 작성한 데이터에 빠져있을 것이고, 새 버전에 코드 스키마에는 optional로 되어있으므로 문제 없음
        - 반대로 옛 버전의 스키마엔 정의되지 않은 필드이므로 무시
    - optional 필드를 제거
        - 해당 필드의 태그는 다시 사용하면 안 된다.
        - required 필드는 삭제가 불가능!!
    - 데이터 타입을 변경할 수 있음
        - 정밀도가 손실되거나 값이 잘릴 수 있음
        - ProtoBuf에서는 단일 `optional` 값을 `repeated`로 변경할 수 있음
        - Thrift는 별도의 리스트 타입을 제공함

### 인코딩 형식 ④ - Avro
- Hadoop의 하위 프로젝트로 시작됨
- Avro IDL과 JSON 스키마를 지원
- 태그 번호를 사용하지 않음

    - Avro IDL
        ```avro
        record Example {
            string                  stringField;
            union { null, long }    numberField = null;
            array<string>           strArrayField;
        }
        ```
        - 필드 이름과 타입이 그대로 들어가있음 

    - Avro IDL을 JSON으로 표현

        ```json
        {
        "type": "record",
        "name": "Example",
        "fields": [
            {"name": "stringField",   "type": "string"},
            {"name": "numberField",   "type": ["null", "long"], "default": null},
            {"name": "strArrayField", "type": {"type": "array", "items": "string"}}
        ]
        }
        ```

- Avro의 Writer Schema와 Reader Schema
    >“Binary encoding does not include field names, self-contained information about the types of individual bytes, nor field or record separators. Therefore readers are wholly reliant on the schema used when the data was encoded.” - From Avro doc

    “바이너리 인코딩에는 필드 이름, 각 바이트의 타입을 자체적으로 설명하는 정보, 필드 또는 레코드 구분자가 포함되지 않는다. 따라서 데이터를 읽는 쪽은 데이터가 인코딩될 때 사용된 스키마에 전적으로 의존한다.” - Avro 문서

    - 그래서 Avro는 Writer Schema와 Reader Schema가 별도의 개념으로 존재함

    - Writer Schema
        - 데이터를 인코딩할 때 작성자 측에서 사용하는 스키마
    - Reader Schema
        - 데이터를 디코딩할 때 읽는 쪽에서 사용하는 스키마
    - 필드 이름을 기준으로 매칭하므로 Writer Schema와 Reader Schema 사이의 필드 순서가 동일할 필요는 없음

    - 스키마 진화 규칙
        - 기본값이 있는 필드는 추가하거나 제거할 수 있음
        - null을 사용하려면 Union 타입에 포함되어 있어야 함
        - optional 또는 required 기능이 없음
        - 데이터 타입을 변경 가능
        - 필드 이름을 변경하는 것은 까다로움
            - Reader Schema에서 Alias를 사용 가능하지만, 필드 이름 변경은 Backward는 호환 가능한데 forward는 호환 안됨
        - Union 타입에 새로운 분기를 추가할 때 주의해야 함
            - 즉, Union 타입에 다른 타입을 넣는 것?도 Backward는 호환 가능한데 forward는 호환 안됨

- Writer Schema 입력 방식
    - 동일한 버전의 레코드가 많이 포함된 대용량 파일
        - 파일 헤더에 스키마를 저장하면 됨
    - 레코드가 개별적으로 기록되는 데이터베이스
        - 레코드 헤더에 버전 번호를 저장하고
        - 데이터베이스에 스키마 버전들을 보관하면 됨
    - 네트워크를 통해 레코드를 전송하는 경우
        - 클라이언트와 서버가 연결을 설정할 때 사용할 스키마를 협상 (주고받음?)

- Avro의 장점
    - Avro는 동적으로 생성되는 스키마에 더 적합
        - 태그를 사용하지 않고 필드 이름을 사용하기 때문
        - 태그를 수동으로 지정하는 방식과 달리 필드 이름을 기준으로 매칭
    - Avro 도구는 다양한 소스로부터 스키마를 생성하는 기능을 지원함
        - Database dump
    - Avro는 정적 타입 언어와 동적 타입 언어 모두에서 사용 가능
        - 자기 설명형 객체 컨테이너 파일(Self-describing Object Container File)
            - write에 스키마를 포함하고 있기 때문에 (Self-describing) 텍스트 파일 열어보듯 쉽게 살펴볼 수 있음

### 스키마와 함께 바이너리 인코딩으로 시작하자? Always use schema w/ binary encoding
- 시간 없어서 그냥 JSON으로 데이터 파이프라인 구성하는 경우가 많은데, 나중에는 JSON 특유의 걸거스함과? 호환성 고려하지 않고 진화해나간 데이터떄문에 고생할 수 있음

- 바이너리 인코딩과 스키마는
    - 공간 효율성이 높음
    - 진화 가능성을 제공 (양방향 호환성 제공)
    - 스키마는 그 자체로 훌륭한 문서이며 데이터의 변경 이력을 보여줌
    - ex. Schema Registry를 사용하는 Kafka

        ![alt text](image-18.png)
        - 스키마 작성자는 스키마 Registry에 스키마를 등록하거나 수정하고
        - 프로듀서는 Registry로부터 스키마를 가져온 다음, 그 스키마대로 데이터 인코딩해서 Kafka 브로커로 보냄
        - Kafka 브로커는 받을 때 Schema Registry를 통해 스키마와 데이터가 일치하는지 검증
        - 컨슈머 또한 Registry로부터 스키마를 가져와서 브로커에서 넘어온 데이터를 디코딩

### 효율적인 데이터 분석을 위한 컬럼형 포맷 - Parquet

![alt text](image-20.png)
- 여러 컬럼들로 구성된 데이터 컬렉션은 테이블 형태로 표현 가능
    - 이 컬럼을 디스크에 쓸 때 문서 단위로 쓸 수 있고(Row-wise) 컬럼 단위로도 쓸 수 있음

- 컬럼형 포맷이 효율적인 이유
    - 분석용 질의는 대부분 컬럼 기반으로 수행됨
        - ex. `SELECT ...`, `WHERE ...` - 개별적인 컬럼을 일부 사용
        - 전체 문서를 읽을 필요가 없음
    - 컬럼 데이터가 메모리에 연속적으로 저장
        - 벡터화 연산(Vectorized Computation)이 가능
            - 데이터 슬롯에 개별 연산이 아니라, 연속된 데이터에 대해 한번의 연산을 수행
        - SIMD(Single Instruction, Multiple Data)를 활용할 수 있음

- Parquet 파일 포맷 - 하이브리드
    - 파일(File): 실제 데이터와 메타데이터를 함께 포함하는 자기 설명형(Self-described) 파일 형식
    - Row Group: 행(Row)들의 부분 집합
        - Parquet은 완벽한 컬럼 포맷은 아니고, Row Group이라고 일부 문서들을 묶어 컬럼 포맷을 구성하는 하이브리드 방식
        - Row Group 사이즈를 키우면 모든 문서들이 하나의 Row Group에 들어가게 됨 - 100% 컬럼 포맷이 될 순 있긴 함?
    - Column Chunk: Row Group 내 특정 컬럼의 데이터
    - Page: Parquet에서 가장 작은 데이터 단위
    - Data Page, Dictionary Page, Index Page

- Parquet 파일 포맷 - Parquet 문서

    ```
    4-byte magic number "PAR1"
    <Column 1 Chunk 1>
    <Column 2 Chunk 1>
    ...
    <Column N Chunk 1>
    <Column 1 Chunk 2>
    <Column 2 Chunk 2>
    ...
    <Column N Chunk 2>
    ...
    <Column 1 Chunk M>
    <Column 2 Chunk M>
    ...
    <Column N Chunk M>
    File Metadata
    4-byte length in bytes of file metadata (little endian)
    4-byte magic number "PAR1"
    ```
    - 파일 시작과 마지막에 Parquet File임을 명시하는 `4-byte magic number "PAR1"`을 넣음
    - 그리고 컬럼 청크 나열
    - 그리고 메타데이터와 메타데이터의 길이를 저장

- Parquet 파일 포맷의 효율성
    - ColumnChunkMetadata에 최소값(Min)과 최대값(Max)을 저장함
        - 조건(Predicate) 필터링과 컬럼 청크(Column Chunk) 프루닝(Pruning)에 유용
        - 컬럼 청크를 통째로 생략할 수 있음
        - ex. age < 10 조건이라면 min >= 10인 모든 청크를 제외(Pruning)할 수 있다.
    - 추가 인코딩 기법
        - Dictionary Encoding
        - Run-Length Encoding(RLE)
    - Parquet에 내장된 Bloom Filter
        - "Compact data structure that over-approximates a set"
            - "집합을 근사적으로 표현하는 공간 효율적인 데이터 구조"
        - 원소 포함 여부를 "확실히 아니다(definitely no)" 또는 "아마 맞다(probably yes)"로 판단
            - 확실히 아니면 없는거고, 아마 맞다면 있는지 없는지 확인해야함
        - 조인(Join)에 유용함

### 마이크로서비스 아키텍처(Micro-Service Architecture)
- 네트워크를 통한 통신에서 가장 고전적인 모델: 클라이언트/서버(Client/Server)
    - 클라이언트가 요청 보내면, 서버는 요청을 받아 처리한 후 응답 보냄
    - 이때, 요청-응답 경로를 API라고 하고, 서버들이 공개하고 있는 API의 묶음으로 서비스(Service)라고 함

- 큰 애플리케이션을 여러 개의 작은 서비스로 분리하고, 각 서비스를 네트워크 API를 통해 제공함
    - 서비스 지향 아키텍처(SOA), 마이크로서비스 아키텍처
    - 관리, 배포, 확장이 쉽다.
    - 서비스 간 의존성은 서로 호환되어야 함

- 웹 서비스(Web Service): HTTP를 통신 프로토콜로 사용
    - REST와 SOAP

- REST, RESTful (Representational State Transfer)
    - 웹(HTTP) 환경에 적합하도록 설계된 아키텍처 스타일
    - 상태를 저장하지 않는(Stateless) 클라이언트-서버 아키텍처이며, URL을 통해 리소스를 식별함
    - HTTP의 `GET`, `POST`, `PUT`, `DELETE` 메서드를 사용하여 작업을 수행
        - `GET` - read, `POST` - create, `PUT` - update, `DELETE` - delete
            - CRUD 수행 가능
        - 캐시 제어(Cache Control), 인증(Authentication), 콘텐츠 타입 협상(Content-Type Negotiation) 등을 지원함
    - 현재 가장 널리 사용되고 선호되는 개발 방식
    - 주로 JSON 형식으로 요청(Request)과 응답(Response)을 주고받음

- SOAP (Simple Object Access Protocol)
    - XML 기반의 언어이며, WSDL(Web Service Description Language)을 사용
        - 코드 자동 생성(Code Generation)을 지원함
        - 직접 작성하기에는 너무 복잡하며, 일부 언어와는 잘 맞지 않음

- 원격 프로시저 호출(Remote Procedure Call, RPC)

    >“Causes a procedure to execute in a different address space which is written as if it were a normal (local) procedure call without explicitly writing the details for the remote interaction” - wikipedia

    "원격 상호작용에 대한 세부 사항을 명시적으로 작성하지 않고도, 마치 일반적인 로컬 프로시저를 호출하는 것처럼 다른 주소 공간에서 프로시저를 실행하도록 하는 기술이다." - Wikipedia

    - 로컬 프로시저와 원격 프로시저의 차이점
        - 예측하기 어려움
            - ex. 타임아웃이 발생했을 때 요청이 서버에 도달했는지 알 수 없음
        - 멱등성(Idempotence)이 보장되지 않으면 재시도로 인해 동일한 작업이 중복 수행될 수 있음
        - 직렬화/역직렬화(SerDe) 오버헤드로 인해 느리고 신뢰성이 떨어질 수 있음
        - 프로그래밍 언어 간 호환성을 고려해야 함

    - 이러한 문제점들을 해결하기 위해 RPC 프레임워크는 계속 발전하고 있음
        - gRPC, Thrift, Finagle, Avro RPC
    
    - RPC, Restful 환경에서는 서비스 호환성(Service Compatibility) 이슈가 있음
        - 레거시 클라이언트 애플리케이션의 업그레이드나 종료를 강제로 제어할 수 없음
        - RESTful API에서는 일반적으로 URL에 버전 번호를 포함함

### Apache Arrow
>“Apache Arrow is a development platform for in-memory analytics. It contains a set of technologies that enable big data systems to process and move data fast. It specifies a standardized language-independent columnar memory format for flat and hierarchical data, organized for efficient analytic operations on modern hardware.”

"Apache Arrow는 **인메모리** 분석(In-Memory Analytics)을 위한 개발 플랫폼이다. 빅데이터 시스템이 데이터를 빠르게 처리하고 이동할 수 있도록 하는 다양한 기술을 포함하고 있다. 또한 평면 데이터와 계층형 데이터를 위한 표준화된 **언어 독립적인(Language-independent) 컬럼형** 메모리 포맷을 정의하여, 현대 하드웨어에서 분석 작업을 효율적으로 수행할 수 있도록 설계되었다."

- 인메모리 분석 데이터 처리를 위한 라이브러리 모음
    - **Zero-copy** 공유 메모리와 RPC 기반 데이터 이동
    - File formats
    - 인메모리 분석 및 쿼리 처리

- 활용 분야
    - Python NumPy, Pandas
        - python이 느리다는 인식 개선됨
    - PySpark Pandas UDF
        - PySpark 고질적인 문제가 UDF인데, Spark 2.0 이후 코드 생성을 구현하게 되면서 PySpark 성능이 많이 개선됨
        - UDF는 JVM과 파이썬 프로세스와 주고받는 인코딩/디코딩 부하때문에 성능이 좋지 않았지만, Arrow를 통해 많이 개선됨

- Apache Arrow 포맷 - 용어
    - 배열(Array)
    - 슬롯(Slot)
    - 버퍼(Buffer)
    - 물리적 레이아웃(Physical Layout): 논리적 의미를 고려하지 않고 비트(Bit) 수준에서 데이터를 표현하는 방식
    - 부모/자식 배열(Parent/Child Arrays): 중첩 타입(Nested Type)의 구조를 표현하기 위한 배열
    - 기본 타입(Primitive Type): 자식 타입 없이 하나의 배열만으로 구성된다.
    - 중첩 타입(Nested Type)
        - ex. `List[T]`
    - 논리 타입(Logical Type)
        - ex. 64비트 레이아웃을 사용하는 Timestamp

- Apache Arrow 포맷 - Array
    - 아래 항목들이 연속된 메모리 공간에 저장되어 있는 것
        - 데이터 타입(Data Type): enum
        - 길이(Length)
        - NULL 개수(Null Count)
        - 유효성 비트맵(Validity Bitmap)
        - 값 버퍼(Value Buffer)
        - Dictionary Encoding이 적용된 배열을 위한 선택적(Dictionary) 정보
        - 중첩 배열(Nested Array)의 경우 자식 배열을 추가로 가짐

    - `[1, null, 2, 4, 8]`
        - Length: 5, Null count: 1
        - Validity bitmap buffer:

            | Byte 0 (validity bitmap) | Bytes 1-63 |
            |---------------------------|------------|
            | 00011101                  | 0 (padding)|
        - Value Buffer:
            | Bytes 0-3 | Bytes 4-7 | Bytes 8-11 | Bytes 12-15 | Bytes 16-19 | Bytes 20-63 |
            |------------|-----------|------------|-------------|-------------|-------------|
            | 1          | unspecified | 2        | 4           | 8           | unspecified (padding) |

    - 가변 길이 타입(Variable Sized Type)의 경우 오프셋(Offset)은 버퍼(Buffer)에 저장됨
    - 메타데이터 직렬화를 위해 Google FlatBuffers를 사용
    - 최대한의 메모리 효율을 제공하는 크로스 플랫폼 직렬화/역직렬화(SerDe) 라이브러리
    - 데이터를 먼저 파싱하거나 언패킹하지 않고 직접 접근할 수 있음

- Apache Arrow Flight RPC
