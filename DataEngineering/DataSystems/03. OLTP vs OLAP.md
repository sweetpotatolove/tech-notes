# OLTP & OLAP

## Online Transaction Processing (OLTP)

### 데이터베이스 내부의 데이터 구조

- 데이터 저장(Set), 데이터 조회(Get)
    - `db_set` 의 성능
        - 단순히 **파일의 끝에 데이터를 추가(Appending)하기 때문에 효율적**이며, 많은 데이터베이스에서 사용하는 Append-Only Log 방식과 유사함
        - 실제 데이터베이스는 동시성(Concurrency), 디스크 공간 회수(Disk Space Reclamation), 오류 처리(Error Handling)와 같은 추가적인 복잡성을 함께 처리
        - 로그(Log)는 데이터베이스에서 반복적으로 사용되는 중요한 개념이며, 반드시 사람이 읽기 쉬운 형태일 필요는 없음

    - `db_get` 의 성능
        - 조회할 때마다 전체 파일을 스캔해야 하므로, **데이터베이스가 커질수록 성능이 좋지 않음**
        - **조회 비용은 O(n)**이며, 레코드 수가 증가할수록 성능이 점점 저하됨

    ```py
    def db_set(key, value):
        with open('database', 'a') as db:
            db.write(f"{key},{value}\n")


    def db_get(key):
        with open('database', 'r') as db:
            lines = db.readlines()

        for line in reversed(lines):
            if line.startswith(f"{key},"):
                return line.split(",", 1)[1].strip()

        return None
    ```
    ```py
    # set data
    db_set("hello1", "world1")
    db_set("hello2", "world2")

    # get data
    print(db_get("hello2"))

    # output
    """
    world2
    """
    ```
    - 코드 설명
        - 전체 파일 스캔..끝에서 추가..

- 인덱싱(Indexing)의 필요성
    - 인덱스는 메타데이터를 추가하여 조회 성능을 향상시키고 데이터를 효율적으로 검색할 수 있도록 함
    - 다양한 유형의 질의를 지원하기 위해 여러 개의 인덱스가 필요할 수 있음

- Trade-off with Indexing
    - 인덱스는 **읽기(Read) 성능을 향상**시키지만, 데이터를 쓸 때마다 인덱스도 함께 갱신해야 하므로 **쓰기(Write) 성능은 저하**됨
        - 기존에는 데이터만 저장하면 됐는데, 이제는 인덱스가 있으니 그에 대한 메타데이터를 다른 곳에 저장해야 함 (=오버헤드: 뭔가를 하기 전에 준비해야하는 것)
    - 데이터베이스는 기본적으로 모든 컬럼에 인덱스를 생성하지 않음
        - 애플리케이션의 조회 패턴을 고려하여 성능 균형을 맞출 수 있도록 필요한 인덱스만 생성함
    
### 해시 인덱스(Hash Indexes)
- 키-값(Key-Value) 데이터 인덱싱
    - 프로그래밍 언어의 해시맵(Hash Map)과 유사한 키-값 저장소(Key-Value Store)에서 주로 사용
    - 인덱싱 전략(Indexing Strategy):
        - 메모리 내 해시맵(In-Memory Hash Map)에 각 키와 데이터 파일의 바이트 오프셋(Byte Offset)을 매핑하여 저장함

- 기본 인덱싱 전략(Basic Indexing Strategy)
    - 파일의 끝에 데이터를 추가한 뒤, 메모리 내 해시맵에 각 키의 저장 위치를 업데이트
    - 해시맵에서 키의 바이트 오프셋을 찾고, 해당 위치에서 값을 읽어옴
    - 바이트 오프셋
        - 바이트에 대한 위치값을 말하는 것
    - 예시1
        - 위에 Hello world에서, hello2 찾을 때 어떠한 byte set에 value가 존재하는지 미리 저장.. 그래서 hello2 찾을 때 바로 바이트 셋으로 포인터가 가서 읽어옴
    - 예시2

        ![alt text](image-7.png)
        - 3개?의 데이터 저장해놓음 - 1234, abcd, xyz
        - 각 데이터는 offset(위치?)에 저장되어 있고, 0번째 위치, 5번째 위치, 10번째 위치에 저장되어 있음
        - 이걸 인덱스로 만든 것?
        - hello, hash, index 라는 key가 있고, 해당되는 value가 각각의 위치(0, 5, 10)


- Bitcask (Riak의 스토리지 엔진에 자주 사용됨)
    - 모든 키가 메모리에 저장될 수 있다면 매우 높은 읽기 및 쓰기 성능을 제공함
    - 값(Value)은 디스크에 저장되며, 최소한의 디스크 I/O만으로 조회할 수 있음
    - 소수의 키가 자주 갱신되는 워크로드에 적합

- 디스크 공간 관리
    - 로그는 **일정한 크기(Size) 또는 시간(Timestamp)**에 도달하면 여러 개의 **세그먼트(Segment)**로 분할됨
        - 세그먼트(Segment): 하나의 조그마한 파일
    - **컴팩션(Compaction)은 중복된 키를 제거하고 가장 최신 버전(최근 데이터)만 유지**
        - 컴팩션(Compaction): 여러 세그먼트를 컴팩트하게(작게) 만드는 방법
    - 컴팩션 과정에서 세그먼트를 병합하여 세그먼트 수를 줄이고 **조회 효율을 향상**시킨다

- 컴팩션과 병합(Compaction and Merging)
    - writeing 프로세스 있고, 백그라운드에 Compaction and Merging 프로세스가 따로 존재함
    - 동작 순서?
        - 백그라운드 프로세스가 세그먼트를 병합한 뒤, 기존 세그먼트를 삭제
        - **각 세그먼트는 자체적인 메모리 내 해시맵을 유지**하며, 조회 시에는 최신 세그먼트부터 먼저 확인
        - **병합 과정을 통해 세그먼트 수를 줄여 읽기(Read) 성능을 최적화**
    - 예시

        - hello (key), 1192(value) 등의 데이터가 들어옴
        - 이때 Compaction 프로세스를 하게되면 데이터를 한꺼번에 모아서 가장 나중 키를 저장함
            - ex. `hello:1192`, `hello:1194`, `hello:1197` -> `hello:1197`
        - 그래서 컴팩트 할 때 가장 나중 것만 읽으면 된다?

        ![alt text](image-9.png)
        - 만약 세그먼트가 여러개라면? Merge가 됨
        - 맨 밑 세그먼트부터 키를 하나씩 찾아가며 컴팩션을 함
        - 맨 마지막에 있는 hello만 저장
        - 나머지 세그먼트에 있는 hello는 버림

- 해시 인덱스의 장점과 한계
    - Append-Only 설계의 장점
        - **순차 쓰기(Appending)는 랜덤 쓰기보다 빠르며**, 특히 HDD(회전식 디스크)에서 큰 이점을 가지며 SSD에서도 성능상 유리
        - 장애 복구(Crash Recovery)와 동시성 관리(Concurrency Management)를 단순화
        - 세그먼트 병합은 시간이 지나며 발생하는 파일 단편화(Fragmentation)를 방지
    
    - 해시 테이블 인덱스의 한계
        - **해시 테이블은 메모리에 모두 올라가야 하므로**, 매우 큰 키 집합에는 적합하지 않음
        - 디스크 기반 해시맵은 랜덤 I/O와 해시 충돌(Hash Collision) 때문에 비효율적
        - **범위 조회(Range Query)**는 각 키를 개별적으로 조회해야 하므로 **비효율적**
        - **메모리 내 해시맵은 시스템 장애(Crash)가 발생하면 사라짐**
            - In-memory이므로 데이터가 날아가는 경우도 생김
        - 복구 과정에서는 세그먼트 파일을 읽어 해시맵을 다시 생성해야 하며, 파일이 클수록 시간이 오래 걸릴 수 있음


### Sorted String Table (SSTable)
- 정렬된 키-값 쌍을 사용하는 로그 구조 저장 방식
    - 로그 구조 저장 방식에서는 키-값 쌍이 순차적으로 기록되며, 동일한 키가 있을 경우 나중에 기록된 값이 우선
    - 세그먼트 파일에 정렬된 키-값 순서를 적용한 형식을 **Sorted String Table(SSTable)**이라고 함
    - 컴팩션(Compaction) 과정을 통해 각 세그먼트에는 동일한 키가 한 번만 존재하도록 유지

        ![alt text](image-10.png)
        - 각 세그먼트들의 인덱스가 있을 때, 이 인덱스들을 정렬시켜놓음
        - Key별로 sorted 
        - 그럼 해시 테이블을 만들 때 맨 앞에 있는 것이 모든 파일에 대해서 가장 빠른거에 해당함
        - 그럼 보다 빨리 테이블을 만들 수 있따..?
        - 이것도 동일하게 맨 마지막에 있는게 최신 데이터이므로 동일한 키만 찾으면 바로 오버라이스? 할 수 있음

- 해시 인덱스 대비 SSTable의 장점
    - 효율적인 병합(Efficient Merging)
        - 동일한 키가 여러 세그먼트에 존재하더라도 **가장 최신 값만 유지**하여 병합할 수 있음
    - 희소 인덱싱(Sparse Indexing)
        - 모든 키에 대한 메모리 인덱스가 필요하지 않으며, 일부 키의 오프셋만 저장하면 정렬된 순서를 이용해 그 사이를 탐색할 수 있음
    - 효율적인 병합 과정(Efficient Merge Process)
        - 세그먼트 병합은 **Merge Sort 알고리즘과 유사**하며, 키를 순서대로 읽어 가장 작은 키부터 출력 파일에 기록함

- 압축과 I/O 대역폭 감소 (Compression and Reduced I/O Bandwidth)
    - 키-값 쌍을 블록 단위로 묶어 압축함으로써 **디스크 사용량과 I/O 대역폭을 줄일 수 있음**
        - 키-값 쌍은 첫번째 것만? 단계별로 읽을 수 있으므로 전체를 읽을 필요가 없다. 읽고 - 처리 - 읽고 - 처리  
    - 희소 인덱스는 각 압축 블록의 시작 위치를 가리켜 읽기 성능을 향상시킴

- 정렬된 문자열 테이블(SSTable)의 생성 과정
    - 쓰기 작업을 위한 **Memtable**
        - 새로운 쓰기 요청은 메모리 내 균형 트리(예: Red-Black Tree)에 저장되며, 이를 Memtable이라고 함
        - 균형(balanced) tree: 리프 노드가 동일하다
        - 그래서 인메모리에 쓸 때 더 빨리 쓸 수 있음 (왤까)
    
    - Memtable을 디스크로 Flush
        - Memtable의 크기가 일정 임계값에 도달(꽉 차게되면)하면 새로운 SSTable로 디스크에 기록됨
        - Memtable은 이미 키 기준으로 정렬되어 있으므로 디스크에 기록하는 과정이 효율적
        - 이전 Memtable이 디스크로 Flush되는 동안 새로운 Memtable이 계속해서 쓰기 요청을 처리힘

- Sorted String Table (SSTable)의 생성과 LSM
    - 읽기 요청 처리 (Read Request Handling)
        - 먼저 Memtable에서 해당 키를 조회 (Memtable에 있는게 가장 최신 데이터니까)
        - 만약 찾지 못하면 디스크에서 **가장 최신 SSTable 세그먼트부터 검색**하고, 필요하면 더 오래된 세그먼트를 차례대로 조회
        - **Bloom Filter**를 사용하여 조회를 최적화
            - Bloom Filter: byte array에서 key 하나를 넣게 되면 첫번째, 두번째것만 블룸 필터에 저장됨. 만약 두번째껄 넣게되면 첫번째, 세번째만 들어가게 됨..?
            - 그럼 첫번쨰, 두번째, 세번째가 다 들어가있다고 볼 수 있음 (이게 뭔말이고)
            - 새로운 키가 들어왔을 때 byte array에서 체크된 것이 모든게 다 있으면 Bloom Filter는 키가 내 DB에 있다고 판단하고 Yes 이렇게 보냄

    - 백그라운드 병합과 컴팩션(Background Merging and Compaction)
        - 백그라운드 프로세스가 주기적으로 오래된 SSTable 세그먼트를 병합하고 컴팩션하여 효율성을 유지함 (Size Tiered 또는 Level Tiered 방식)
        - 이것이 **LSM(Log-Structured Merge)** Tree의 핵심 아이디어

### B-Tree
- B-트리는 관계형 데이터베이스와 비관계형 데이터베이스 모두에서 **가장 널리 사용되는 인덱스 구조**

- B-트리의 주요 특징
    - 키-값 쌍을 SSTable처럼 정렬된 상태로 유지하지만, **B-트리는 가변 크기 세그먼트 대신 일반적으로 4KB 크기의 고정 크기 블록(Page)을 사용**함
    - 각 페이지는 키와 자식 페이지에 대한 참조를 포함하며, 조회를 시작하는 루트 페이지(Root Page)가 하나 존재함

        ![alt text](image-11.png)
        - 페이지: 딕셔너리
        - 어떠한 레퍼런스가 있고, 레퍼런스 사이에 어떠한 range가 어떤 레퍼런스에 있다..? 페이지는 사전이라고 생각하면 됨
        - 10, 20이 range. 10과 20 사이에 레퍼런스는 다른 페이지를 인디케이트? 하고있다. 그리고 다른 페이지는 10과 20 사이의 모든 ragne를 가지고 있다. 
        - 결과적으로 리프 노드에 보면, 21 ~ 30 사이의 ragne가 있는 페이지가 있는데 거기서 데이터를 가져옴
        - 말 그대로 루트 페이지에서 range를 찾고, 찾고.. 그렇게 찾아야하는 페이지 범위를 줄여서 data value를 찾아냄
    
    - 분기 계수(Branching Factor): 자식 페이지 참조의 개수
        - 자식 페이지가 몇 개가 되느냐?

- B-Tree에서의 키 수정 및 추가
    - 키 수정(Update)
        - 해당 리프 페이지(Leaf Page)를 찾아 수정한 후 디스크에 다시 기록
    - 키 추가(Add)
        - 페이지에 공간이 없으면 두 개의 **페이지로 분할(Split)**되고, **부모 페이지가 함께 갱신**

- 균형 트리 구조 (Balanced Tree Structure)
    - B-트리는 깊이가 **O(log n)인 균형 트리 구조**를 유지하므로, 대부분의 데이터베이스는 3~4단계만 거쳐도 효율적인 조회가 가능
    - 4KB 페이지와 분기 계수 500을 사용하는 4단계 B-트리는 최대 256TB의 데이터를 저장할 수 있음

- B-트리 최적화 (B-Tree optimizations)
    - **Write-Ahead Log(WAL)**을 이용한 장애 복구
        - B-트리 구현은 일반적으로 장애 복구를 보장하기 위해 Write-Ahead Log(WAL)를 사용
        - WAL은 B-트리의 모든 변경 사항을 페이지에 반영하기 전에 먼저 기록하여, 장애 발생 후 데이터베이스를 일관된 상태로 복구할 수 있도록 함
        - 즉, 일단 디스크 저장 후 메모리에 저장하는 방식
        - 메모리 에러났을 때 디스크에 저장되어있는걸 가져오면 됨?
        - 디스크 저장하고, 페이지 업데이트 시키고, 제대로 됐으면 디스크에 저장한거 없애고..

    - 동시성 제어 (Concurrency Control)
        - 키를 찾아가는 도중 페이지가 바귀면 에러남
        - 여러 스레드가 동시에 트리에 접근할 때 일관성 없는 상태를 방지하기 위해, B-트리는 Latch(경량 락)를 이용한 세심한 동시성 제어가 필요
        - 로그 구조(Log-Structured) 방식은 병합이 백그라운드에서 수행되고, 세그먼트가 원자적으로 교체되므로 질의에 영향을 주지 않아 구조가 더 단순함
        
### LSM Tree vs. B-Tree
- LSM Tree
    - 로그 시스템, 시계열 데이터베이스, NoSQL 데이터베이스(Cassandra, HBase, LevelDB 등)처럼 **쓰기(Write)가 많은 워크로드에 적합**

- B-Tree
    - 범위 조회(Range Query)와 단건 조회(Point Lookup)가 빈번한 MySQL, PostgreSQL과 같은 관계형 데이터베이스처럼 **읽기(Read)가 많은 워크로드에서 널리 사용**

### 키-값 인덱스를 넘어선 인덱스 구조 (Indexing Structures Beyond Key-Value Indexes)
- 기본 인덱스와 보조 인덱스 (Primary vs. Secondary Indexes)
    - 기본 인덱스(Primary Index): 레코드를 고유하게 식별
    - 보조 인덱스(Secondary Index): **고유하지 않은 컬럼에 대해서도 효율적인 조회를 가능**하게 하며, 키-값 인덱스를 기반으로 구성
        - 여러 인덱스를 그룹지어놓은 것?

- 인덱스 저장 방식
    - Heap File은 데이터와 인덱스를 분리하여 저장하므로 데이터 중복은 줄일 수 있지만, 실제 데이터 위치를 가리키는 포인터가 필요
        - Heap File: ?
    - Clustered Index는 실제 행(Row) 데이터를 인덱스 내부에 함께 저장하므로 읽기 성능은 향상되지만 저장 공간과 쓰기 오버헤드가 증가함
        - Clustered Index: ?

- 다중 컬럼 및 다차원 인덱스 (Multi-Column and Multi-Dimensional Indexes)
    - 결합 인덱스(Concatenated Index)
        - 여러 컬럼을 하나의 키로 결합한다. (ex. (lastname, firstname))
    - 다차원 인덱스(Multi-dimensional Index)
        - 위도와 경도 같은 공간 데이터를 여러 차원에서 효율적으로 범위 조회할 수 있도록 함
        - 전체적인 맵을 블록단위로 나눠서 인덱스를 만들 수 있..다?

- 전문 검색 및 퍼지 인덱스 (Full-Text and Fuzzy Indexes)
    - 전문 검색(Full-Text Search)은 편집 거리(Edit Distance)나 동의어 확장(Synonym Expansion) 등의 기법을 이용하여 오탈자가 있거나 유사한 키도 검색할 수 있도록 함
    - 유저가 검색 시 키워드 에러나는 경우
        - 미스 스펠링하는 경우에 사용

### In-Memory Databases
- 인메모리 데이터베이스와 디스크 기반 데이터베이스 (In-Memory vs. Disk-Based Databases)
    - 인메모리 데이터베이스는 모든 데이터를 RAM에 저장하여 디스크 I/O 오버헤드를 제거함으로써 **속도를 향상**시킴
    - **내구성(Durability)은 로그(Log), 스냅샷(Snapshot), 복제(Replication)를 통해 확보**할 수 있음

- 인메모리 데이터베이스의 장점
    - 디스크에 영속적으로 저장하기 위해 필요한 직렬화(Serialization) 오버헤드가 없음
    - 특수한 자료구조를 제공 (ex. 우선순위 큐를 지원하는 Redis)

- 안티 캐싱(Anti-Caching) 방식
    - 메모리가 가득 차면 가장 오랫동안 사용되지 않은 데이터(LRU)를 디스크로 내보내고, 다시 접근하면 메모리로 불러오는 방식으로 운영체제의 가상 메모리와 유사

- 비휘발성 메모리(NVM; Non-Volatile Memory)
    - 미래 데이터베이스 스토리지 엔진 설계에 영향을 줄 수 있는 차세대 메모리 기술


## Online Analytics Processing (OLAP)

- OLAP란 무엇인가?
    - 온라인 분석 처리(Online Analytical Processing, OLAP)는 일반적으로 **대용량 데이터를 대상으로 복잡한 데이터 분석과 의사결정을 지원**하기 위해 설계된 시스템의 한 종류
    - OLAP 시스템은 **과거 데이터를 조회하여 인사이트, 추세, 패턴을 도출하는 데 주로 사용되며, 비즈니스 인텔리전스(BI)를 위한 목적**으로 많이 활용됨

### OLTP vs. OLAP

| Aspects | **OLTP** | **OLAP**|
| ------- | -------- | ------- |
| **주요 읽기 패턴 (Main Read Pattern)** | 고유 식별자를 기반으로 소수의 특정 레코드를 조회한다. | 많은 레코드를 요약하여 합계나 평균 등을 계산한다.                                                               |
| **주요 쓰기 패턴 (Main Write Pattern)** | 사용자 동작에 따라 최소한의 지연으로 데이터를 빠르게 갱신한다. | 배치 처리나 연속적인 데이터 스트림을 통해 대량의 데이터를 적재한다. |
| **사용 목적 (Usage)** | 온라인 플랫폼을 이용하는 일반 사용자나 고객이 사용한다. | 기업의 분석가가 비즈니스 의사결정을 위한 인사이트를 얻기 위해 사용한다. |
| **데이터 표현 (Data Representation)** | 시스템의 최신 데이터를 반영한다. | 시간에 따라 축적된 데이터를 나타내며 과거의 행동과 추세를 보여준다. |
| **데이터셋 크기 (Dataset Size)** | GB ~ TB | TB ~ PB |
| **트랜잭션 유형 (Transaction Type)**             | 짧고 상호작용이 많은 트랜잭션 (Short, interactive transactions) | 복잡한 분석 트랜잭션 (Complex analytical transactions) |
| **쿼리 복잡도 (Query Complexity)** | 빠른 응답의 단순한 질의 | 집계(Aggregation)를 포함한 복잡한 질의 |
| **지연 시간 (Latency)** | 낮은 지연 시간, 실시간 응답 | 상대적으로 높은 지연 시간, 배치 처리에서는 허용 가능 |

### 데이터 웨어하우징(Data Warehousing)
- 데이터 웨어하우징(Data Warehousing)
    - 다양한 데이터 소스로부터 **대량의 데이터를 수집, 저장, 관리하여 분석과 리포팅을 위한 중앙 저장소(Central Repository)에 통합**하는 과정
    - 비즈니스 인텔리전스(BI)와 의사결정을 지원하기 위해 대규모 조직에서 널리 사용됨

- Data Warehousing Process

    ![alt text](image-12.png)
    - 고객 관계 관리 (CRM; Customer Relationship Management), 전사적 자원 관리 (ERP; Enterprise Resource Planning), 청구 시스템 (Billing), 로그 등 모든 유저 이벤트들을 OLTP 을 통해 ETL을 함
    - ETL: 추출, 변환, 로딩
        - 보통 Spark, Flink 사용
        - 데이터가 들어오는 파이프라인은 Kafka 많이 사용함
    - ETL을 통해 정기적으로 Data Warehouse에 데이터를 로딩
    - 그럼 분석가들이 Reporting, Analytics, Data Mining 등을 함

- 데이터 웨어하우징의 핵심 포인트
    - 중앙 집중형 데이터 저장소(Centralized Data Repository)
        - 여러 OLTP 시스템이나 다양한 데이터 소스의 데이터를 통합하여 분석을 위한 통합된 관점을 제공함
    - 분석에 최적화(Optimized for Analytics)
        - OLTP 시스템과 달리, 데이터 웨어하우스는 대규모 데이터셋을 대상으로 하는 복잡한 질의와 데이터 분석에 최적화되어 있음
    - 읽기 전용(Read-only)
        - 데이터 웨어하우스는 운영 데이터의 읽기 전용 복사본을 저장하므로, 분석 질의가 운영 시스템에 영향을 주지 않음
    - ETL 프로세스
        - 데이터를 원본 시스템에서 추출(Extract)하고, 분석에 적합한 형태로 변환(Transform) 및 정제(Cleaning)한 뒤 데이터 웨어하우스에 적재(Load)함
    - 비즈니스 인텔리전스 지원(Supports Business Intelligence)
        - 분석가가 리포트를 생성하고, 추세를 파악하며, 더 나은 비즈니스 의사결정을 내릴 수 있도록 지원
    - 대규모 기업에서 주로 사용(Common in Large Enterprises)
        - 대기업은 데이터의 규모와 복잡성 때문에 데이터 웨어하우스를 활용하며, 소규모 기업은 더 단순한 도구를 사용할 수도 있음

### 분석을 위한 스키마: Star Schema
- 스타 스키마(Star Schema)
    - 데이터 웨어하우스에서 데이터를 구성하기 위해 널리 사용되는 단순한 데이터베이스 스키마
    - **중앙의 테이블과 이를 둘러싼 여러 테이블의 구조**가 별(Star) 모양과 비슷하여 스타 스키마라고 불림

        ![alt text](image-13.png)

- Star Schema의 주요 특징
    - 팩트 테이블(Fact Table)
        - 스타 스키마의 중앙 테이블
        - 판매량, 매출, 판매 수량과 같은 정량적 데이터(주로 트랜잭션 데이터)를 저장하며, 측정값(예: 매출액)과 차원 테이블을 연결하는 키를 함께 저장함
    - 차원 테이블(Dimension Table)
        - 팩트 테이블을 둘러싸는 테이블로, 팩트 데이터와 관련된 설명 속성(Descriptive Attributes)을 저장함
        - 상품 정보, 고객 정보, 시간 정보 등 데이터를 해석하는 데 필요한 맥락(Context)을 제공

- Star Schema의 장점
    - 구조가 단순하고 이해하기 쉽다.
    - 테이블 간 조인이 적어 질의 성능이 빠르다.
    - 대부분의 리포팅 및 분석 업무에 적합하다.

### 분석을 위한 스키마: Snowflake Schema
- 스노우플레이크 스키마(Snowflake Schema)
    - 스타 스키마를 확장한 형태이며, 더 정규화되어 있음
    - **차원 테이블이 다시 하위 차원 테이블(Sub-dimension Table)로 분리**되어 전체 구조가 눈송이(Snowflake)처럼 보이기 때문에 스노우플레이크 스키마라고 불림

        ![alt text](image-14.png)

- Snowflake Schema의 주요 특징
    - 팩트 테이블(Fact Table)
        - 스타 스키마와 마찬가지로, 스노우플레이크 스키마 역시 측정값(Measures)과 키(Keys)를 저장하는 중앙 팩트 테이블을 가짐
    - 정규화된 차원 테이블(Normalized Dimension Tables)
        - 차원 테이블을 여러 개의 관련 테이블로 정규화하여 데이터 중복을 줄임
        - ex. 하나의 Customer 테이블 대신 Customer, Address, Region 테이블로 분리할 수 있음

- Snowflake Schema의 장점
    - 데이터 중복을 제거하여 저장 공간을 절약한다.
    - 복잡한 관계를 더 유연하게 표현할 수 있다.

- Snowflake Schema의 단점
    - **테이블 간 조인이 많아져 질의 성능이 느려**질 수 있다.
    - 설계가 더 복잡하여 이해하고 관리하기가 어려울 수 있다.


### 저장 구조(Storage Layout)
- OLTP (행 지향 저장 방식)
    - 데이터를 **행(Row)** 단위로 저장
    - 하나의 행에는 하나의 레코드에 대한 모든 컬럼이 포함되며, 연속된 행들이 디스크에 함께 저장됨
        - ex. 고객 정보 테이블에서는 이름, 주소, 전화번호 등 한 고객의 모든 정보가 하나의 행에 저장된다.
        - ex. PostgreSQL, MySQL

- OLAP (열 지향 저장 방식)
    - 데이터를 **열(Column)** 단위로 저장
    - 각 컬럼은 별도로 저장되며, 특정 컬럼의 모든 값(ex. 모든 고객 이름)이 연속된 블록에 함께 저장됨
        - ex. 같은 테이블에서 고객 이름 컬럼은 함께 저장되고, 전화번호 컬럼은 별도로 함께 저장된다.
        - ex. Redshift, BigQuery, Snowflake

    ![alt text](image-15.png)

- 열 지향 저장에서의 컬럼 압축(Column Compression in Column-Oriented Storage)
    - 열 지향 저장 방식은 컬럼 값에 반복되는 패턴이 많기 때문에 **압축에 매우 적합**
    - 압축은 디스크에서 읽어야 하는 데이터 양을 줄여 디스크 처리량(Throughput) 요구를 감소시킴
        - 압축하면 I/O가 줄기 때문데 더 빨리 읽을 수 있고, 필더도 더 빨리 할 수 있음
    - 컬럼의 데이터 타입에 따라 다양한 압축 기법을 사용할 수 있음
        - ex. Bitmap Encoding

- 컬럼 압축: 비트맵 인코딩(Bitmap Encoding)
    - 5개의 서로 다른 상품 ID(30, 68, 69, 31, 42)를 가지는 Product 컬럼을 생각해 보자. 데이터가 1,000개의 행으로 구성되어 있다면 다음과 같다.
        - 각 상품 ID마다 별도의 비트맵(Bitmap)이 생성됨
        - 상품 ID가 30인 경우, 비트맵은 1000100000...처럼 표현될 수 있으며, 값이 1인 위치는 해당 행에 상품 ID 30이 존재함을 의미
        - **질의(Query)는 비트 연산(`AND`, `OR`)을 이용하여 여러 비트맵을 빠르게 결합하거나 필터링할 수 있음**
            - ex. `WHERE product_id IN (30, 68)`은 상품 30과 68의 비트맵을 불러온 뒤 OR 연산을 수행하여 둘 중 하나에 해당하는 행을 찾는다.
    - 효율적인 저장 공간(Efficient Storage)
        - 컬럼의 고유 값(Distinct Value)이 적을수록 Bitmap Encoding은 저장 공간을 크게 줄일 수 있음
    - 빠른 질의 성능(Fast Query Performance)
        - 필터링, 그룹화(Group By), 개수 집계(Count) 등의 질의를 비트 연산으로 빠르게 수행할 수 있음
    
- 열 지향 저장에서의 행 정렬 (Sort row in Column-Oriented Storage)
    - 행 기반 정렬(Row-based Sorting)
        - 데이터는 열 단위로 저장되지만, 행 전체를 기준으로 정렬함
        - 데이터베이스는 자주 조회되는 컬럼(ex. 날짜 기반 조회를 위한 `date_key`)을 기준으로 정렬 키를 선택
    - 질의 최적화(Query Optimization)
        - `date_key`를 기준으로 정렬되어 있다면 날짜 조건을 사용하는 질의는 전체 데이터를 스캔하지 않고 필요한 구간만 빠르게 조회할 수 있음
    - 다중 정렬 키(Multiple Sort Keys)
        - 두 번째, 세 번째 컬럼(ex. `product_sk`)을 보조 정렬 키로 사용할 수 있음
        - 관련된 데이터를 함께 배치하여 필터링과 집계를 더욱 효율적으로 수행할 수 있음
    - 압축 효과(Compression Benefit)
        - 정렬은 압축 효율을 높dla
        - 특히 첫 번째 정렬 키는 Run-Length Encoding과 같은 기법으로 반복되는 값을 더욱 효과적으로 압축할 수 있음
        - ex. wwwbbwwww => 3w1b4w (8bytes -> 6bytes)

- 열 지향 저장에서의 쓰기 (Writes in Column-Oriented Storage)
    - 열 지향 저장, 압축, 정렬은 데이터 웨어하우스의 읽기 중심(Read-heavy) 질의를 최적화하여 조회 성능을 향상시킴
    - 하지만 이러한 최적화에는 단점이 있음.
        - **데이터를 수정하려면 정렬과 압축 상태를 유지하기 위해 전체 컬럼 파일을 다시 작성해야 하므로 쓰기 작업이 어려워짐**
    - **LSM Tree(Log-Structured Merge Tree)**는 먼저 **메모리에서 쓰기를 처리한 뒤, 이를 디스크의 컬럼 파일과 한꺼번에 병합**함으로써 이 문제를 해결함
    - 쓰기 데이터는 먼저 정렬된 메모리 구조에 저장되며, 이후 질의 성능에 영향을 주지 않으면서 디스크 데이터와 효율적으로 병합됨

- 사전 집계(Pre-Aggregation): **데이터 큐브(Data Cube)**
    - 데이터를 **다차원 구조(Multi-dimensional Structure)**로 구성하여 다양한 관점에서 빠르게 탐색할 수 있도록 함

        ![alt text](image-16.png)
        - ex. 판매 데이터 큐브는 시간(연도, 월), 상품(Product), 지역(Region)을 차원으로 가질 수 있다.
    - 여러 차원에서 데이터를 Slicing, Dicing 및 분석하는 데 적합함
    - 빠른 질의를 위해 데이터를 미리 집계(Pre-Aggregation)해 둠

- 사전 집계(Pre-Aggregation): **머티리얼라이즈드 뷰(Materialized View)**
    - 자주 실행되거나 복잡한 질의의 성능을 높이기 위해 특정 질의의 결과를 미리 저장함
        - ex. 지역별 총매출을 질의할 때마다 다시 계산하는 대신, 미리 계산된 결과를 저장해 두어 더 빠르게 조회할 수 있다.
    - 반복적으로 수행되는 OLAP 질의의 계산 시간을 줄이는 데 적합
    - 집계(Aggregation), 조인(Join) 등 복잡한 연산 결과를 미리 저장해 둘 수 있음
