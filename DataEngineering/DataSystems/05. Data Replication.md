### 요약
- 이 장의 질문: 데이터를 여러 노드에 복사해두는 이유와, 그 복사본들이 서로 어긋나지 않게(또는 어긋나더라도 사용자가 이상함을 못 느끼게) 관리하는 방법
- 복제의 목적 3가지: **지연 시간 감소**(사용자와 가까운 복제본) / **가용성 향상**(하나 죽어도 서비스 지속) / **읽기 처리량 향상**(여러 대로 분산)

- 단일 리더 복제의 기본 구조: **리더=쓰기 전담, 팔로워=읽기 전담** + 리더가 변경 사항을 팔로워로 전파
    - 전파 시점(복제 전략): 동기(일관성↑ 지연↑) / 비동기(속도↑ 유실 위험) / 준동기(팔로워 일부만 동기 — 실무 절충안)
    - 전파 내용(복제 로그): 문장 기반 → WAL 전송 → Row-Based(CDC) → 트리거 기반
        - 리더 구현에 종속적일수록(WAL) 일관성·효율은 좋지만 유연성이 낮고, 독립적일수록(CDC·트리거) 유연하지만 오버헤드가 큼
        - CDC가 최근 데이터 파이프라인(Kafka 연동)에서 널리 쓰이는 절충점

- 운영 관점: 팔로워 추가(스냅샷+로그 위치 기록 후 Catch Up) / 장애 조치(감지→승격→전환, **Split-Brain** 방지가 핵심 리스크)

- 복제 지연이 낳는 문제와 해결책 — 비동기 복제라면 반드시 마주치는 세 가지 "이상해 보이는 순간"과 그 해법
    - 쓰기 후 읽기 일관성: 내가 방금 쓴 게 안 보이는 문제
    - 단조 읽기: 방금 본 것보다 줄어들어 보이는(시간 역행) 문제
    - 일관된 접두사 읽기: 결과가 원인보다 먼저 보이는(순서 역전) 문제

## 단일 리더 복제(Single Leader Replication)

### 왜 복제(Replication)가 필요한가?
- 사용자와 가까운 위치에 데이터를 유지하여 **지연 시간(Latency)을 줄이기 위해**
    - 지연 시간(Latency): 요청부터 응답까지 걸리는 시간
    - 데이터가 물리적으로 사용자와 멀리 떨어져 있으면, 네트워크 왕복 자체에 시간이 걸림 
        - 빛의 속도가 유한하니까 거리가 멀수록 지연은 물리적으로 피할 수 없음
    - ex. 서울 사용자가 미국 서버의 DB만 조회한다면 매 요청마다 태평양을 왕복 → 서울 근처에 복제본을 두면 그 지연이 사라짐

- 시스템 구성 요소에 장애가 발생하더라도 계속 동작할 수 있도록 하여 **가용성(Availability)을 높이기 위해**
    - 서버 한 대가 죽어도 복제본이 있으면 서비스가 계속됨

- 읽기 요청을 처리할 수 있는 서버 수를 늘려 **읽기 처리량(Read Throughput)을 향상시키기 위해**
    - 읽기 요청을 여러 복제본에 분산 → 한 대가 감당하던 부하를 N대가 나눠 처리

### 복제 방식(Replication Mechanism)
- "리더가 몇 개냐"로 복제 방식을 구분함
    - 단일 리더 복제(Single Leader Replication): 쓰기를 받는 노드가 하나
    - 다중 리더 복제(Multi Leader Replication): 쓰기를 받는 노드가 여러 개
    - 리더리스 복제(Leaderless Replication): 리더라는 개념 자체가 없음

### 리더 기반 복제(Leader-based Replication)
- 리더(Leader)와 팔로워(Follower)
    - Active-Passive 또는 Master-Slave라고도 불림
    - 최근에는 "Master-Slave"라는 표현의 함의 문제로 대부분의 시스템(Redis, MySQL 등)이 Leader-Follower 또는 Primary-Replica라는 용어로 옮겨감

- 리더(Leader / Primary): **쓰기(Write)** 전담
    - 모든 데이터 변경은 반드시 리더에서 먼저 일어남
    - 쓰기가 끝나면 리더가 그 변경 사항을 팔로워들에게 전파(복제)함
    - 팔로워가 최신 상태를 유지하도록 리더가 관리

- 팔로워(Follower / Replica): **읽기(Read)** 담당
    - 클라이언트가 팔로워에서 데이터를 조회 → 읽기 부하가 여러 대로 분산됨 (위에서 본 "읽기 처리량 향상"의 실제 구현체)
    - 리더의 변경 사항을 동기 또는 비동기로 전달받음
    - 리더에 장애가 나면, 팔로워 중 하나가 **새로운 리더로 승격**될 수 있음


### 복제 전략(Replication Strategy)
- 팔로워가 리더의 변경 사항을 **언제** 받아 적용하는지에 대한 전략. 크게 세 가지:
    1. 동기식(Synchronous)
    2. 비동기식(Asynchronous)
    3. 준동기식(Semi-Synchronous)

    ![alt text](image-24.png)
    - **동기식(Synchronous)**
        - Process A(리더)가 요청을 보내고, Process B(팔로워)의 응답이 올 때까지 **기다린 후에** 다음을 진행
        - 리더는 팔로워가 데이터를 정상적으로 받았다는 확인을 받아야만 그 쓰기를 "완료"로 간주 (클라이언트에게도 그제서야 성공 응답)
        - 장점
            - 팔로워가 리더와 항상 같은 데이터를 보장 → **데이터 일관성**이 높음
        - 단점
            - 팔로워의 응답을 기다리는 만큼 **지연 시간이 늘어남**, 팔로워가 느리거나 죽으면 리더의 쓰기 자체가 멈출 위험
    - **비동기식(Asynchronous)**
        - Process A가 요청을 보낸 뒤 응답을 기다리지 않고 **바로 다음 작업을 계속**(continue the process), 응답은 나중에 별도로 받음
        - 리더는 팔로워의 확인을 기다리지 않고 곧바로 클라이언트에게 쓰기 완료를 알림
        - 장점
            - 팔로워 상태와 무관하게 리더가 빠르게 응답 → **가용성과 처리 속도** 우수
        - 단점
            - 리더가 죽었는데 팔로워가 아직 그 변경을 못 받았다면, 그 데이터는 **유실**될 수 있음 (일시적 불일치)
    - **준동기식(Semi-Synchronous)**
        - 리더에 팔로워가 여러 대 있을 때, **그중 하나만 동기식으로, 나머지는 비동기식**으로 두는 절충안
        - ex. 팔로워 3대 중 1대만 동기 → 그 1대는 항상 최신 데이터를 보장(장애 시 안전하게 승격 가능) + 나머지 2대는 비동기라 리더의 쓰기 성능은 거의 그대로 유지
        - 완전 동기(모든 팔로워 대기, 느리지만 매우 안전)와 완전 비동기(안 기다림, 빠르지만 유실 위험) 사이의 실무적 타협점
            - MySQL의 반동기 복제(Semi-Sync Replication)가 이 방식의 실제 구현


### 추가 팔로워 구성하기(Configuring additional followers)
![alt text](image-25.png)

- 데이터와 트래픽이 늘어나 팔로워를 추가해야 할 때의 절차
    1. 새로운 팔로워 노드를 준비한다 (하드웨어·네트워크 설정)
    2. 리더의 스냅샷(Snapshot)을 생성한다
        - 스냅샷 = 특정 시점의 데이터 전체 상태를 찍은 사본
        - 이때 **스냅샷을 찍은 시점이 리더의 로그(WAL 등) 상에서 정확히 어느 위치였는지**도 함께 기록해둠 
            - ex. MySQL의 binlog position, PostgreSQL의 LSN
        - 이 위치 정보가 없으면, 나중에 "스냅샷 이후로 어떤 변경 사항부터 적용해야 하는지"를 알 방법이 없음
    3. 생성한 스냅샷을 새로운 팔로워로 복사한다
    4. 팔로워에 스냅샷을 적용한다 
        - 이 시점 팔로워는 "스냅샷 찍힌 순간"의 리더 상태와 같아짐 (그 이후 변경은 아직 반영 안 됨)
    5. 복제를 시작하고 최신 데이터까지 따라잡는다(Catch Up)
        - 2번에서 기록해둔 로그 위치부터 시작해서, 그 이후 리더에 쌓인 변경 사항을 순서대로 재생(Replay)
        - 다 따라잡으면 팔로워가 리더와 실시간으로 동기화된 상태가 됨
    6. 복제 상태를 모니터링하고 정상 동작하는지 검증한다
        - **무엇을 모니터링하나:**
            - **복제 지연(Replication Lag)**: 팔로워가 리더보다 얼마나 뒤처져 있는지 (초 단위, 또는 로그 위치 차이)
            - **복제 프로세스의 생존 여부**: 복제 스레드가 에러 없이 계속 로그를 받아 적용하고 있는지 (죽어있으면 팔로워가 그 순간부터 멈춰버림)
            - **데이터 정합성**: 주기적으로 리더와 팔로워의 데이터를 체크섬 등으로 비교해서 실제로 같은 내용인지 검증 (복제는 됐다고 나오는데 내용이 미묘하게 달라지는 경우가 실무에서 실제로 있음)

### 장애 조치(Failover) 발생 시
1. 장애를 감지한다
    - **Heartbeat**: 리더가 주기적으로 "나 살아있다"는 신호를 보내고, 팔로워(또는 모니터링 도구)가 이걸 받아 리더의 생존을 확인
    - 신호가 **일정 시간(약 30초)** 동안 안 오면 리더가 죽었다고 판단
        - 이 시간을 너무 짧게 잡으면: 순간적인 네트워크 지연에도 "죽었다"고 오판(False Positive)해서 불필요한 장애 조치가 발생
        - 너무 길게 잡으면: 실제로 죽었을 때 장애 조치가 시작되기까지 그만큼 서비스가 먼저 멈춰 있음
        - 그래서 30초는 "오탐과 늦은 감지 사이의 실무적 타협점"
    - 운영팀이 즉시 인지하도록 알림(Alert) 설정
2. 팔로워를 새로운 리더로 승격한다
    - 여러 팔로워 중 **가장 최신 상태**(= 리더와 가장 가까운 데이터를 가진 팔로워)를 선택 
        - 데이터 유실을 최소화하기 위함
    - **Split-Brain 방지**: 옛 리더가 실제로는 완전히 죽은 게 아니라 일시적인 네트워크 단절이었을 뿐이라면?
        - 장애 감지 시스템은 "죽었다"고 오판해서 새 리더를 승격시킴
        - 그런데 잠시 후 옛 리더가 네트워크가 복구되며 다시 살아 돌아오면, **리더가 동시에 두 개** 존재하는 상황이 됨
        - 이 상태에서 서로 다른 클라이언트가 각기 다른 리더에 쓰기를 하면 **데이터가 두 갈래로 갈라짐(Diverge)** 
            - 나중에 병합이 매우 어렵거나 불가능해짐
        - 방지책: 옛 리더를 강제로 종료시키는 메커니즘(STONITH 등), 또는 "몇 번째 리더인지"를 나타내는 임기(Term/Epoch) 번호를 둬서 오래된 임기의 리더가 쓰기를 시도하면 거부하는 방식 등
3. 클라이언트 연결을 새로운 리더로 전환한다
    - 클라이언트 설정 또는 로드 밸런서의 라우팅 대상을 재설정
4. 나머지 팔로워들을 업데이트한다
    - 남은 팔로워들이 새 리더를 바라보도록 복제 관계를 재구성
5. 이중화(Redundancy)를 복구한다
    - 죽은 서버 자리를 메울 새 팔로워를 추가해서, 장애 이전과 같은 수의 복제본을 다시 확보
    - 위에서 본 "추가 팔로워 구성하기" 절차가 여기서 실제로 쓰임
6. 데이터 무결성(Data Integrity)을 감사(Audit)하고 검증한다
    - 승격 과정에서 유실되거나 중복 적용된 데이터가 없는지 확인
7. 장애 조치 절차를 테스트하고 문서화한다
    - 실제 장애가 아니어도 정기적으로 장애 조치를 리허설해서 절차가 실제로 작동하는지 검증 

### 복제 로그 설정(Setting up Replication Logs)
> 리더에서 팔로워로 "무엇을" 전달할지에 대한 4가지 방식. 뒤로 갈수록 리더 구현에 덜 종속되지만, 그만큼 오버헤드가 커지는 트레이드오프가 있음

- **문장 기반 복제(Statement-Based Replication)**
    - 리더에서 실행된 SQL 문장 자체를 복제 로그에 기록 → 팔로워가 그 SQL을 동일하게 재실행
    - 단순하고 결정적(Deterministic)인 아이디어: 
        - "같은 명령을 리더와 팔로워 양쪽에서 각자 실행하면 같은 결과가 나올 것"이라는 전제
    - 장점
        - SQL 문장만 기록하므로 구현이 간단하고 로그 용량이 작음
    - 단점
        - `NOW()`, `RAND()` 같은 **비결정적 함수**를 쓰면 리더와 팔로워가 각자 다른 시점·다른 값으로 실행해서 결과가 달라짐 → 데이터 불일치
        - 각 문장을 팔로워에서 다시 처음부터 실행해야 하므로, 동시성이 높은 환경에서는 (리더에서의 실행 순서와 팔로워에서의 실행 순서가 미묘하게 달라질 수 있어) 성능 저하나 결과 불일치 위험

- **Write-Ahead Log(WAL) 전송**
    - 디스크 블록 단위의 저수준 변경 사항을 그대로 리더에서 팔로워로 전송
    - "SQL을 다시 실행"하는 게 아니라 "리더가 실제로 디스크에 쓴 바이트 변경분을 그대로 복사"하는 방식이라 **강한 일관성**을 가짐 
        - 팔로워가 리더의 물리적 복사본에 가까워짐
    - 장점
        - 실제 변경 사항 그대로를 복제하므로 일관성이 보장됨
        - 변경분만 전송하므로 처리량이 높은 대규모 DB에서도 효율적
    - 단점
        - WAL은 **DB 엔진의 내부 저장 포맷에 종속**됨 → 팔로워가 리더와 정확히 같은 DB 버전·저장 포맷을 써야 함 (다른 버전이면 WAL 포맷 자체가 안 맞을 수 있음)
        - 로그 크기가 커질 수 있어 디스크·네트워크 대역폭 부담

- **논리적(Row-Based) 로그 복제 — Change Data Capture(CDC)**
    - 디스크 블록 전체가 아니라, **행(Row) 단위의 논리적 변경 사항**("이 행이 이렇게 바뀌었다")을 기록해서 전송
    - 많은 DB에 **내장 기능**으로 제공되며(ex. MySQL의 Row-based binlog), WAL과 달리 물리적 저장 포맷에 안 묶여 있어서 **DB 버전이 다르거나 심지어 다른 종류의 DB 사이의 복제도 가능**
        - ex. MySQL의 변경 사항을 CDC로 뽑아서 Kafka를 거쳐 Elasticsearch나 데이터 웨어하우스에 반영하는 파이프라인이 실무에서 흔함(Debezium 등)
    - 장점
        - 팔로워가 리더와 다른 버전·다른 DB 시스템이어도 사용 가능 → 유연성 높음
        - 특정 테이블·특정 행만 골라서 복제 가능
    - 단점
        - 행 단위로 기록하다 보니 WAL 전송보다 저장·처리 비용이 더 듦
        - 작은 행 변경이 매우 잦으면 오버헤드가 커짐

- **트리거 기반 복제(Trigger-Based Replication)**
    - DB의 트리거(특정 이벤트 발생 시 자동 실행되는 사용자 정의 코드) 기능을 이용해, 변경 사항을 별도 테이블·로그에 직접 기록 → 팔로워가 그걸 읽어 적용
    - **사용자가 로직을 직접 정의**하므로 세밀한 제어가 가능 (어떤 조건일 때 뭘 기록할지 마음대로 짤 수 있음)
    - 장점
        - 원하는 변경 사항만 선택적으로 기록 가능, 복잡한 데이터 변환도 가능
    - 단점
        - 스키마가 바뀌면 트리거도 같이 수정해야 해서 관리 부담
        - 변경마다 추가 코드가 실행되므로 리더 자체의 성능이 저하될 수 있음

- 네 방식을 고르는 기준 — 하나의 축(스펙트럼)으로 보면 이해하기 쉬움

    > [리더 구현에 종속적, 일관성 강함] ← WAL 전송 — Row-Based(CDC) — 문장 기반 — 트리거 기반 → [구현 독립적, 유연함, 오버헤드 큼]

    - **WAL 전송**: 리더의 저장 엔진 내부 포맷을 그대로 씀 → 팔로워가 리더와 동일한 DB·버전이어야 함(종속 최대) / 대신 물리적으로 동일한 복사본이라 일관성이 가장 강하고 오버헤드도 적음
    - **Row-Based(CDC)**: 저장 포맷과 분리된 논리적 변경 기록이라 DB 버전이 달라도, 심지어 다른 DB 시스템끼리도 가능 → 종속성이 낮고 유연함
    - **문장 기반 / 트리거 기반**: SQL이나 사용자 코드로 동작하므로 구현 종속은 더 낮지만, 비결정성·트리거 관리 같은 별도 리스크와 오버헤드가 붙음

    - CDC(Row-Based)가 최근 데이터 파이프라인(Kafka 연동 등)에서 널리 쓰이는 이유가 바로 이 위치
        - **강한 일관성을 어느 정도 유지하면서도 DB 종류를 넘나드는 유연성**까지 챙긴 절충점이라서

### 복제 지연(Replication Lag) 해결 방법
- 복제 지연(Replication Lag)이란?
    - 비동기 복제에서는 리더가 팔로워의 확인을 기다리지 않고 쓰기를 완료하므로, **팔로워가 리더의 최신 상태를 따라잡는 데 시간차**가 생김
    - 이 "리더는 이미 반영했는데 팔로워는 아직 반영 못 한" 시간 간격이 복제 지연
    - 문제는 클라이언트가 우연히 **뒤처진 팔로워**에서 읽기를 하면, 방금 일어난 변경이 안 보이거나 옛날 데이터를 보게 될 수 있다는 것
    - 아래 세 가지는 각각 "그래도 사용자 입장에서 이상하게 느껴지지 않도록" 보장해주는 서로 다른 수준의 일관성 규칙

- ① 쓰기 후 읽기 일관성(Read-after-write Consistency)
    - **자기 자신이 방금 쓴 데이터**는, 복제 지연과 무관하게 항상 곧바로 조회할 수 있도록 보장
    - 구현 방식
        - 쓰기 직후의 읽기 요청은 **리더** 또는 **이미 그 변경 사항을 반영한 팔로워**로 라우팅
        - ex. "이 사용자의 최근 쓰기가 1초 이내였다면 리더에서 읽기" 같은 규칙, 혹은 세션에 "마지막 쓰기 시점"을 기록해두고 그 이후 읽기 요청에 활용
    - 장점
        - 사용자가 자신의 변경 사항을 즉시 확인 가능 → 일관된 사용자 경험
            - ex. SNS에 글을 올렸는데 새로고침했더니 안 보이면 "어 실패했나?" 하고 혼란스러움 — 이걸 방지
        - 세션·사용자 정보로 라우팅이 가능한 시스템에서는 구현이 비교적 간단
    - 단점
        - 리더에서 직접 읽는 경우가 늘어나 리더의 읽기 부하 증가 → 팔로워로 읽기를 분산시키려던 원래 목적(복제의 이유 중 하나)이 일부 희석됨
        - 여러 디바이스에서 로그인한 사용자라면 "자기 자신"의 범위를 디바이스 간에도 일관되게 추적해야 해서 분산 환경에서 관리가 복잡해짐

- ② 단조 읽기(Monotonic Reads)
    - 한 사용자가 **한 번 읽은 데이터보다 더 오래된 버전을 그 이후에 다시 보지 않도록** 보장
    - 최신 데이터를 보장하진 않지만(여전히 뒤처진 팔로워를 읽을 수 있음), 한 번 앞으로 나아간 뒤로는 **절대 뒤로 가지 않음**
        - ex. 댓글을 새로고침했는데 어떤 요청은 지연이 적은 팔로워A(최신 댓글 5개 보임), 다음 새로고침은 지연이 큰 팔로워B(최신 댓글 3개만 보임)로 라우팅되면 → 댓글 개수가 5개에서 3개로 **줄어드는** 이상한 경험을 하게 됨. 단조 읽기는 이런 "시간 역행"을 막음
    - 구현 방식
        - 같은 사용자의 읽기 요청을 항상 **같은 팔로워**로 라우팅
            - ex. 사용자 ID의 해시값으로 팔로워를 고정
    - 장점
        - 데이터가 일관되게 앞으로만 진행 → "이전 상태로 되돌아가는(Time Travel)" 혼란스러운 경험 방지
    - 단점
        - 여전히 최신이 아닐 수 있음(그저 뒤로 안 갈 뿐)
        - 사용자·세션별로 "어느 팔로워를 봤는지" 추적해야 해서 라우팅 로직이 복잡해짐

- ③ 일관된 접두사 읽기(Consistent Prefix Reads)
    - 여러 데이터 간에 **인과 관계(원인-결과)가 있을 때, 그 순서가 뒤바뀐 채로 보이지 않도록** 보장
    - "접두사(Prefix)"라는 이름의 의미
        - A→B→C 순서로 일어난 일이라면, 이후에 보이는 결과는 항상 그 순서의 **앞부분(접두사)까지만**
        - 즉 `[]`, `[A]`, `[A,B]`, `[A,B,C]`는 가능해도 `[A,C]`(B를 건너뛰고 C만)나 `[C]`(A,B 없이 C만) 같은 순서 깨짐은 없음
    - ex. 채팅에서 "질문: 저녁 뭐 먹지?" → "답변: 치킨 어때?" 순서로 메시지가 갔는데, 복제 지연 때문에 어떤 사용자에게는 답변("치킨 어때?")이 질문보다 먼저 보이면 무슨 소리인지 알 수 없음.
    - **여러 파티션·리더에 걸친 데이터**에서 특히 문제가 됨
        - 파티션마다 복제 지연이 다르면, 인과관계가 있는 두 데이터가 서로 다른 파티션에 있을 때 순서가 꼬일 수 있음
        - 그래서 해결책도 "인과적으로 연관된 쓰기는 같은 파티션에 두기" 같은 접근이 쓰임
    - 장점
        - 관련 데이터의 논리적 순서 유지 → 사용자가 이벤트를 올바르게 이해 가능
        - 금융 거래, 이벤트 로그처럼 순서가 의미 자체를 결정하는 시스템에 필수적
    - 단점
        - 복제 노드 간 순서를 추적·보장해야 해서 구현이 복잡함
        - 중간 단계 데이터가 복제될 때까지 기다려야 할 수 있어 지연이 발생

### 정리
| 보장 | 막아주는 문제 | 적합한 사례 |
|---|---|---|
| 쓰기 후 읽기 일관성 | "내가 방금 쓴 게 안 보임" | SNS 게시글 작성, 문서 편집처럼 사용자가 자신의 변경을 즉시 확인해야 하는 경우 |
| 단조 읽기 | "아까 봤던 것보다 줄어들어 보임" (시간 역행) | 최신이 아니어도 괜찮지만 역행은 안 되는 대시보드, 로그 처리 시스템 |
| 일관된 접두사 읽기 | "결과가 원인보다 먼저 보임" (순서 역전) | 채팅, 금융 거래처럼 인과 순서 자체가 의미인 애플리케이션 |

- 세 가지 보장 수준은 서로 배타적이지 않고, 필요에 따라 **함께 적용**할 수 있음 
    - ex. 쓰기 후 읽기 일관성 + 단조 읽기를 동시에 보장하는 시스템도 흔함
