### 요약
- 이 장의 질문: 내 객체를 어떤 데이터 모델로 저장할 것인가 — **데이터의 모양(트리/그물망)과 접근 패턴(읽기/쓰기, 방향)이 답을 결정**

    - 관계형 모델: 정규화(중복 제거)와 조인이 기본. 다대다·양방향 조회에 강함
        - Schema-on-Write / 정규화 = 쓰기 최적화 → OLTP
    - 문서 모델: 객체를 생긴 그대로(JSON) 저장 → Impedance Mismatch 해소, Data Locality
        - 전제: One-to-Few 트리 + 전체를 한 번에 읽는 패턴 / Schema-on-Read / 비정규화 = 읽기 최적화
    - 그래프 모델: 다대다 관계가 매우 빈번할 때 (Property Graph, Triple Store)
        - 킬러 기능: 가변 길이 경로(`WITHIN*0..`) — SQL 재귀 CTE 30줄 = Cypher 4줄
    - 분석용 스키마(DW): Star / Snowflake / OBT
        - 불변 데이터라 갱신 불일치가 없음 → 비정규화가 정당화되는 환경

- 선언형 질의 언어(SQL, Cypher, SPARQL): 무엇(What)만 명시, 어떻게(How)는 옵티마이저가 결정
- 그 외: GraphQL(프론트엔드용 데이터 조회), 이벤트 소싱·CQRS(쓰기 로그와 읽기 뷰 분리), Dataframe(분석·ML용)

## Data Models

- 데이터 모델은 계층(Layer)으로 쌓여 있음 — 각 계층은 "아래 계층 위에 어떻게 표현할 것인가"의 문제
    - ① App Developer: 실 세계를 객체, 데이터 구조, API로 모델링
        - ex. 쇼핑몰 — 구매자, 판매자, 상품, 결제를 클래스/API로 표현
    - ② Data Structure in Storage: ①의 객체를 저장하기 위한 범용 데이터 모델
        - JSON, XML, 관계형 테이블, 그래프 중 선택
        - 실 세계 데이터 모델을 저장하기 위한 방법을 의미하는 데이터 모델
    - ③ DB Software: ②의 데이터 모델을 메모리·디스크 위의 바이트로 표현
        - 이 바이트 표현이 질의(Query), 검색(Search), 처리(Process) 방식을 결정함
    - ④ Hardware: 바이트를 전기 신호, 자기장, 광 신호 등 물리적 형태로 표현
    - 개발자가 주로 하는 선택은 ①→② 사이: **내 객체를 어떤 데이터 모델(테이블? 문서? 그래프?)로 저장할 것인가** → 이 장의 주제

- 추상화 (Abstraction)
    - 각 계층은 아래 계층의 복잡성을 깔끔한 데이터 모델 뒤에 숨김 (Hides complexity in each layer)
        - ex. SQL을 쓸 때 디스크의 바이트 배치를 몰라도 되고, 바이트를 다룰 때 전압을 몰라도 됨
    - 계층이 분리되어 있어서 각 분야의 사람들(앱 개발자, DB 엔지니어, 하드웨어 엔지니어)이 효율적으로 협업 가능 (Effective collaboration)

- 어떤 데이터 모델과 질의 언어로 우리의 데이터를 표현하는 것이 가장 좋을까?

## Declarative Query Language 선언형 질의 언어

- SQL, Cypher, SPARQL, Datalog

- 무엇을(What) 원하는지만 명시한다 (Only specify)
    - 결과로 얻을 데이터의 형태(패턴): `SELECT FROM`
    - 결과의 조건: `WHERE`
    - 데이터 변환: `ORDER BY`, `GROUP BY`, `AGG`

- 어떻게(How) 달성할지는 명시하지 않는다
    - 어떤 인덱스를 탈지, 어떤 순서로 조인할지 같은 알고리즘은 지정하지 않음
    - → 그 결정은 DB의 **쿼리 옵티마이저(Query Optimizer)**가 담당
    - 알고리즘을 한 줄씩 직접 기술하는 명령형(Imperative) 프로그래밍 언어와 대비됨

- Abstraction 추상화
    - "어떻게"가 숨겨져 있으므로, DB는 **기존 쿼리를 한 줄도 바꾸지 않고** 내부 실행 방식을 개선할 수 있음
        - ex. 새 인덱스 추가, 병렬 처리 도입 → 쿼리는 그대로, 성능만 향상
        - Without breaking changes, DB can improve query performance

## Relational Model vs Document Model

- 관계형(Relational) 모델
    - 데이터를 관계(Relation) 형태로 구성함: SQL의 테이블(Table)에 해당
    - 관계(Relation)는 순서가 없는 튜플(Tuple)의 집합임: SQL의 행(Row)에 해당
    - 현재까지 가장 널리 사용되는 데이터 모델임

- NoSQL과 NewSQL의 등장
    - NoSQL: 관계형 모델의 한계를 극복하기 위해 등장
        - 유연한 스키마, 수평 확장성(Scale-out), 오픈소스 채택이 주 목적
    - NewSQL: 관계형 모델과 SQL, 트랜잭션은 그대로 유지하면서 NoSQL 수준의 분산 확장성을 제공하려는 시도
        - ex. Google Spanner, CockroachDB, TiDB

- 문서(Document) 모델
    - 데이터를 JSON 형태의 자기완결적인 문서(Document)로 표현함
    - MongoDB, CouchDB
    - 대부분의 관계형 데이터베이스에서도 JSON 컬럼 타입을 지원함 (PostgreSQL의 `jsonb` 등)


- 왜 Document 모델을 사용할까?
    - 객체-관계형 불일치(Object-Relational Mismatch, Impedance Mismatch)
        - 애플리케이션 코드의 객체는 중첩 구조(객체 안에 리스트, 리스트 안에 객체)인데, 관계형 모델은 평평한 행(Row)과 열(Column)로만 저장함
        - 그래서 객체 하나를 저장하려면 여러 테이블로 쪼개고, 다시 읽으려면 조인으로 재조립해야 함 → 이 변환 계층이 번거로움
    - 이 변환을 대행해주는 라이브러리: `ORM (Object-Relational Mapping)`
        - ex. Python의 SQLAlchemy, Java의 JPA/Hibernate
    - ORM의 문제점
        - 변환 계층 자체가 복잡함
        - 관계형 OLTP 데이터베이스에서만 잘 동작함
            - OLTP란? 트랜잭션을 지원하고, 잦은 쓰기 연산을 효율적으로 처리하며, 주로 서비스 운영에 사용되는 DB 유형
            - ex. PostgreSQL, MySQL, Oracle
        - 비효율적이며 N+1 Query 문제가 발생함
            - N+1 Query: 목록 1번 조회 + 목록의 각 항목마다 연관 데이터를 1번씩(N번) 추가 조회하게 되는 문제
            - ex. 게시글 목록(쿼리 1번)을 가져온 뒤, 각 글의 작성자 이름을 작성자 ID로 글마다 따로 조회(쿼리 N번) → 총 N+1번의 쿼리 발생. 조인 한 번이면 될 일을 ORM이 자동 생성한 코드가 나눠서 실행하는 것
        - 객체 모델 정의가 변경될 때 스키마 마이그레이션 오버헤드가 발생함
    - ORM의 장점
        - Productivity: 반복적인 SQL 작성 없이 객체 조작만으로 개발 가능
        - Caching: 조회한 객체를 세션 안에서 재사용
        - 스키마 마이그레이션 도구 제공: 객체 정의 변경 → 마이그레이션 스크립트 자동 생성
            - ex. SQLAlchemy의 Alembic, Django의 migrate

### Normalization, Denormalization, Joins
- 정규화 (Normalization): 중복을 제거하는 것
    - 핵심 수단: 문자열(Text) 대신 ID를 사용
        - 사람에게 의미 있는 정보(이름, 로고)는 한 곳에만 저장하고, 나머지는 ID로 참조
        - ID는 그 자체로 의미가 없으므로 바뀔 일이 없음 → 참조가 깨지지 않음
    - 문자열 대신 ID를 쓰면 얻는 것
        - 일관된 표기와 철자 유지 ("Netflix" vs "netflix" 문제 제거)
        - 동일한 문자열로 인한 모호성 방지 (동명의 다른 회사 구분 가능)
        - 수정 및 갱신이 쉬움 (한 곳만 수정)
        - 다국어(Localization) 지원 용이 (ID는 그대로, 표시 이름만 언어별로)
        - 검색 성능 향상

    - 정규화에 대한 고민
        - 정규화: 기계에는 효율적이지만, 사람이 이해하기에는 덜 직관적 (ID 참조를 따라가야 전체가 보임)
        - 비정규화: 사람이 이해하기에는 더 직관적 (한 눈에 전체가 보임)

- 정규화된 데이터는 관계형 모델에서 Join을 통한 추가 조회(Lookup)가 필요함

    ```sql
    SELECT profiles.*, experiences.organization
    FROM profiles
    JOIN experiences ON profiles.id = experiences.user_id
    WHERE profiles.id = 100
    ```
    - id가 100인 사람이 다녔던 회사 목록 → `user_id`로 조인

- 문서 모델에서도 정규화(ID 참조)를 하면 조인에 해당하는 연산이 필요함

    ```js
    db.profiles.aggregate([
        { $match: { _id: 100 }},
        { $lookup:
            {
                from: "experiences",
                localField: "user_id",
                foreignField: "_id",
                as: "organization"
            }
        }
    ])
    ```
    - `$match`: id가 100인 문서를 찾음 (SQL의 WHERE)
    - `$lookup`: profiles의 `user_id`와 experiences의 `_id`가 일치하는 문서를 가져와 결합 (SQL의 JOIN에 해당)
    - 즉, 문서 모델이라고 조인이 사라지는 게 아니라, 정규화하는 순간 `$lookup`이라는 이름으로 돌아옴
        - 그리고 일반적으로 관계형 DB의 조인보다 최적화가 약함

- 정규화의 트레이드오프(Trade-off)
    - ex. 회사 로고가 바뀌면?
        - 비정규화: 그 회사가 박힌 모든 레코드를 업데이트 → 대량 쓰기 + 도중 실패 시 불일치
        - 정규화: 해당 조직(Organization) 행 하나만 업데이트
    - 정규화된 데이터
        - **쓰기에 유리**: 한 곳만 고치면 되고, 중복이 없어 일관성 유지가 쉬움
        - 조회는 조인이 필요해서 상대적으로 느림
        - → 쓰기가 잦고 일관성이 중요한 OLTP에 적합
    - 비정규화된 데이터
        - **읽기에 유리**: 조인 없이 한 번에 읽음
        - 쓰기는 중복된 모든 사본을 갱신해야 해서 비용이 크고, 일관성 문제 발생 가능
        - → 읽기(집계) 위주이고 데이터가 잘 안 바뀌는 대규모 OLAP에 적합
    - 요약: **정규화 = 쓰기 최적화, 비정규화 = 읽기 최적화**

- 다대일(Many-to-One), 다대다(Many-to-Many) Relationships

    - Many-to-One: person ↔ region

    - Many-to-Many: person ↔ organization
        - 여러 사람이 여러 조직에 속함
        - 관계형 모델: 연결 테이블(Associative/Join Table)로 구현


- 다대다(Many-to-Many) 관계를 조회하는 방법
    - 다대다는 **양방향 조회**가 필요하다는 게 핵심 문제
    - 비정규화 방식: 양쪽 문서에 서로의 ID를 저장
        - person 문서에 org_id 목록, organization 문서에 user_id 목록
        - 단, 한쪽만 갱신되면 데이터 불일치 발생 가능
    - 정규화 방식: 보조 인덱스(Secondary Index)로 역방향 조회를 해결
        - 관계형: 연결 테이블의 user_id, org_id 각각에 인덱스 생성
        - 문서 모델: experience 배열 내부 객체의 org_id 필드에 인덱스 생성 (MongoDB의 Multikey Index)
        - → 인덱스가 "org_id → 그 값을 가진 문서들"의 역방향 지도를 대신 유지해줌

### 데이터 분석을 위한 스키마 - Stars, Snowflakes
- 데이터 웨어하우스(DW)에서 주로 쓰이는 데이터 모델
    - Star schema, Snowflake schema, Dimensional modeling (차원 모델링), One Big Table (OBT)

- Fact와 Dimension
    - Fact Table: **사건(Event)** 하나가 행 하나 — 판매, 클릭, 주문 등
        - 측정값(Measure): 주로 숫자 (수량, 금액)
        - 차원 참조: 차원 테이블을 가리키는 FK들
    - Dimension Table: 사건의 **맥락** — 누가(customer), 무엇을(product), 어디서(store), 언제(date), 어떻게/왜(promotion)
    - 한 문장으로: "무슨 일이 있었나"는 Fact, "그 일의 6하원칙"은 Dimension

- Star schema

    ![alt text](image-4.png)
    - 가운데 Fact Table(fact_sales), 주변에 차원 테이블들이 별 모양으로 배치
    - fact_sales의 각 행: Order_ID(PK) + store_sk, product_sk, customer_sk, promotion_sk(각 차원을 가리키는 FK)
    - 분석 쿼리 예: "3월에 부산 매장에서 프로모션으로 팔린 상품별 매출" → Fact를 중심으로 필요한 차원만 조인

- Snowflake schema
    - Star schema의 차원을 **한 단계 더 정규화**한 것
        - ex. dim_product가 다시 dim_brand, dim_category를 참조
    - 차원이 하위 차원으로 세분화 → 눈송이 결정 모양
    - 중복은 줄지만 조인이 늘어남 → 실무에서는 분석 쿼리 단순함을 위해 Star를 선호하는 경우가 많음

- Star와 Snowflake의 공통점
    - Fact → Dimension 방향의 다대일 관계가 기본 구조
    - **다대다 관계는 단순화를 위해 비정규화하는 것이 보편적**

- One Big Table (OBT)
    - 모든 차원을 Fact에 합쳐 **완전히 비정규화**한 하나의 넓은 테이블
    - 저장 공간은 더 쓰지만 조인이 아예 없어 조회가 가장 빠름
    - 컬럼 지향 저장(*03. OLTP vs OLAP.md 참고*)과 결합하면 중복 컬럼이 압축이 잘 되어 공간 낭비도 완화됨

- 분석 환경(OLAP)에서는 비정규화가 정당화되는 이유
    - 과거 데이터이며, 일반적으로 한 번 적재되면 변경되지 않음 (Immutable)
    - → 비정규화의 최대 약점인 "갱신 시 불일치"가 애초에 발생할 일이 없음
    - 일관성과 쓰기 오버헤드의 중요도가 낮고, 읽기 속도가 전부인 환경

### 문서(Document) 모델을 언제 사용할 것인가?
- 데이터가 문서와 유사한 구조일 때
    - 일대다(One-to-Few) 트리 구조이고, **전체 트리를 한 번에 불러오는** 접근 패턴일 때 적합
        - ex. 프로필 페이지: 열 때마다 경력·학력 전부를 같이 보여줌 → 문서 하나 = 화면 하나
    - 이런 경우 관계형 테이블(조인으로 재조립)보다 자연스러움

- 배열의 순서가 자연스럽게 보존됨
    - 관계형의 행은 순서가 없어서(순서가 필요하면 별도 정렬 컬럼 필요) 이것도 문서 모델의 소소한 장점

- 단점: 문서 내부의 중첩 항목을 직접 참조하기 어려움
    - 관계형에서는 어떤 행이든 PK로 직접 지칭 가능하지만, 문서 내부 항목은 독립된 ID가 없음
    - "user 100의 문서 안에서 → experience 배열의 → 2번째 항목"처럼 **경로(위치)로만 접근** 가능 (Position only)
    - 배열 순서가 바뀌면 참조가 깨질 수 있음

- 스키마가 유연함: Schema-on-Read vs Schema-on-Write
    - Schema-on-Write (관계형): 스키마를 **쓰는 시점**에 강제
        - 스키마에 안 맞는 데이터는 INSERT 자체가 에러
    - Schema-on-Read (문서): 저장할 때는 아무 구조나 허용하고, **읽는 시점**에 애플리케이션 코드가 구조를 해석
        - 스키마가 없는 게 아니라, 스키마 검증의 시점이 다른 것 (암묵적 스키마)
    - 문서 모델은 서로 상이한 구조의 데이터들을 하나의 컬렉션에 넣고 싶을 때 좋음

- 스키마 변경(새 필드 추가)이 쉬움
    - 문서 모델: 마이그레이션 없이 코드에서 처리

        ```js
        if (user && user.name && !user.first_name) {
            // Documents written before Dec 8, 2023 don't have first_name
            user.first_name = user.name.split(" ")[0];
        }
        ```
        - 옛 문서는 그대로 두고, 읽을 때 없으면 채움 (Schema-on-Read 방식의 대응)

    - 관계형 모델: 마이그레이션 오버헤드

        ```sql
        ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL;
        UPDATE users SET first_name = split_part(name, ' ', 1);    -- PostgreSQL
        UPDATE users SET first_name = substring_index(name, ' ', 1);    -- MySQL
        ```
        - 전체 테이블 UPDATE는 대형 테이블에서 오래 걸리고 잠금(Lock) 부담이 있음

- 그 밖의 차이점
    - 데이터 지역성(Data Locality)의 양면
        - 문서는 하나의 연속된 바이트 덩어리로 저장 → 문서 **전체를 읽을 때** 매우 효율적
        - 대신 문서 일부만 수정해도 (특히 문서 크기가 커지는 수정이면) **문서 전체를 다시 써야** 하는 경우가 많음 → 큰 문서일수록 수정 오버헤드 증가
        - → "전체를 읽고, 드물게 쓰는" 패턴에 최적
        - 최근에는 관계형 DB(PostgreSQL jsonb 등)와 NoSQL이 서로의 모델을 부분 지원하므로 섞어서 사용 가능 (하이브리드)

    - Query Language
        - 관계형: 표준 SQL
        - 문서 모델: 제품 고유(Proprietary)의 쿼리 언어 (MongoDB Aggregation Pipeline 등)
        - 같은 질의("상어 종류별 월별 관측 수 집계")의 비교:

            ```sql
            SELECT date_trunc('month', observation_timestamp) AS observation_month,
                sum(num_animals) AS total_animals
            FROM observations
            WHERE family = 'Sharks'
            GROUP BY observation_month;
            ```
            ```js
            db.observations.aggregate([
                { $match: { family: "Sharks" } },
                { $group: {
                    _id: {
                        year: { $year: "$observationTimestamp" },
                        month: { $month: "$observationTimestamp" }
                    },
                    totalAnimals: { $sum: "$numAnimals" }
                } }
            ]);
            ```

## Graph-Like Data Model

- 다대다 관계가 **매우 빈번**할 경우 그래프 모델이 자연스러움
    - 문서 모델: 관계가 트리(계층) 모양일 때 / 그래프 모델: 관계가 그물망 모양일 때
    - ex. 소셜 네트워크(사람-사람), 웹 링크(페이지-페이지), 도로망

- 구성 요소: 정점(Vertex)과 간선(Edge)
    - 내부적으로 인접 리스트(Adjacency List)나 인접 행렬(Adjacency Matrix)로 구현 가능

- 정점은 어떤 종류의 객체든 될 수 있음 → 하나의 그래프에 서로 다른 타입의 데이터(사람, 장소, 이벤트)를 함께 저장 가능

- 종류
    - Property Graph model: Neo4j, Memgraph, KùzuDB
    - Triple-Store model: Datomic, AllegroGraph, Blazegraph

- Different query language
    - Cypher, SPARQL, Datalog, GraphQL

- 그래프 모델 예시

    ![alt text](image-5.png)
    - Taylor는 Texas에서 태어나(born_in) Tokyo에 살고(lives_in) Ruby와 결혼함(married)
    - 위치들은 within 간선으로 계층 연결: Texas → United States → North America

### Property Graph와 Cypher
- Property Graph
    - 정점 (Vertex): ID / 레이블(객체 종류: Person, Location) / 나가는 간선 / 들어오는 간선 / 속성(key-value)
    - 간선 (Edge): ID / 레이블(관계 종류: BORN_IN, WITHIN) / 꼬리 정점(Tail, 출발) / 머리 정점(Head, 도착) / 속성(key-value)
    - 화살표로 기억: 꼬리 ──레이블──> 머리

- Property Graph를 관계형 스키마로 표현

    ```sql
    CREATE TABLE vertices (
        vertex_id   integer PRIMARY KEY,
        label       text,
        properties  jsonb
    );

    CREATE TABLE edges (
        edge_id     integer PRIMARY KEY,
        tail_vertex integer REFERENCES vertices (vertex_id),
        head_vertex integer REFERENCES vertices (vertex_id),
        label       text,
        properties  jsonb
    );

    CREATE INDEX edges_tails ON edges (tail_vertex);
    CREATE INDEX edges_heads ON edges (head_vertex);
    ```
    - 테이블 단 2개로 그래프 전체 표현 가능
    - tail/head 양쪽에 인덱스 → "이 정점에서 나가는 간선"과 "이 정점으로 들어오는 간선" 모두 빠르게 조회 = **양방향 탐색**

- Property Graph의 특징
    - 어떤 정점이든 간선으로 연결 가능하며 타입 제약이 없음
    - 레이블과 속성으로 하나의 그래프에 다양한 정보 저장
    - 간선 테이블은 다대다 관계의 연결 테이블(조인 테이블)과 구조가 유사함 — 그래프 모델은 "모든 것이 다대다"인 세계
    - 데이터 모델링 유연성이 매우 높고, 변화 용이성(Evolvability)에 적합

- Cypher Query Language
    - Neo4j 그래프 데이터베이스를 위해 만들어졌으며, 이후 openCypher 표준으로 발전함
    - 데이터 생성:
    
        ```cypher
        CREATE
            (namerica :Location {name:'North America',  type:'continent'}),
            (usa      :Location {name:'United States', type:'country'  }),
            (texas    :Location {name:'Texas',         type:'state'    }),
            (taylor   :Person   {name:'Taylor'                         }),
            (texas) -[:WITHIN ]-> (usa) -[:WITHIN]-> (namerica),
            (taylor) -[:BORN_IN]-> (texas)
        ```

        - `(정점)`, `-[:간선]->` — ASCII 아트로 그래프를 그리듯 씀

    - ex. 대한민국에서 태어나 미국으로 이주한 모든 사람의 이름:

        ```cypher
        MATCH
            (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (:Location {name:'South Korea'}),
            (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'United States'})
        RETURN person.name
        ```
        - `-[:WITHIN*0..]->`: WITHIN 간선을 **0번 이상 반복**해서 따라간다는 가변 길이 경로(Variable-Length Path)
            - 성남에서 태어난 사람: 성남 →within→ 경기 →within→ 대한민국 (2번)
            - 대한민국이 직접 출생지로 기록된 사람: 0번
            - 몇 단계인지 미리 몰라도 되는 게 핵심
        - 선언형이므로 실행 방법은 DB가 선택:
            - 방법 1: 모든 사람을 스캔해서 출생지·거주지 필터링
            - 방법 2: 반대로 두 위치 정점(South Korea, United States)에서 시작해 within 간선을 역방향으로 따라 내려간 뒤, BORN_IN/LIVES_IN 간선을 역으로 타고 사람에 도달
            - 어느 쪽이 빠른지는 데이터 분포에 따라 다르고, 선택은 옵티마이저의 몫 (선언형의 장점 재등장)


- 같은 질의를 SQL로 하면? — 재귀 CTE
    - 관계형에서 간선 탐색 = 조인. 그런데 `WITHIN*0..`처럼 **조인 횟수를 미리 알 수 없는** 질의가 문제
        - 성남은 3단계, 서울은 2단계... 몇 번 조인할지 데이터를 봐야 앎
    - 해결책: 재귀 공통 테이블 표현식 (Recursive CTE, `WITH RECURSIVE`)
        - CTE: 쿼리 안에서 임시 결과 집합에 이름을 붙여 재사용하는 문법
        - 재귀 CTE: **자기 자신을 참조**하는 CTE — "시작 집합"에서 출발해 "확장 규칙"을 더 이상 새 행이 없을 때까지 반복

        ```sql
        WITH RECURSIVE

        -- in_usa: 미국 '안에 있는' 모든 위치의 vertex_id 집합
        in_usa(vertex_id) AS (
            SELECT vertex_id FROM vertices
                WHERE label = 'Location' AND properties->>'name' = 'United States'
            UNION
            SELECT edges.tail_vertex FROM edges
                JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
                WHERE edges.label = 'within'
        ),

        -- in_south_korea: 대한민국 안에 있는 모든 위치 (같은 패턴)
        in_south_korea(vertex_id) AS (
            SELECT vertex_id FROM vertices
                WHERE label = 'Location' AND properties->>'name' = 'South Korea'
            UNION
            SELECT edges.tail_vertex FROM edges
                JOIN in_south_korea ON edges.head_vertex = in_south_korea.vertex_id
                WHERE edges.label = 'within'
        ),

        -- born_in_south_korea: 대한민국(안의 어딘가)에서 태어난 사람들
        born_in_south_korea(vertex_id) AS (
            SELECT edges.tail_vertex FROM edges
                JOIN in_south_korea ON edges.head_vertex = in_south_korea.vertex_id
                WHERE edges.label = 'born_in'
        ),

        -- lives_in_united_states: 미국(안의 어딘가)에 사는 사람들
        lives_in_united_states(vertex_id) AS (
            SELECT edges.tail_vertex FROM edges
                JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
                WHERE edges.label = 'lives_in'
        )

        SELECT vertices.properties->>'name'
        FROM vertices
        -- 두 집합에 모두 속한 사람의 이름
        JOIN born_in_south_korea
            ON vertices.vertex_id = born_in_south_korea.vertex_id
        JOIN lives_in_united_states
            ON vertices.vertex_id = lives_in_united_states.vertex_id;
        ```

    - in_usa의 동작 (재귀의 실체):
        - 1회차: `{United States}`
        - 2회차: within 간선의 head가 US인 것들의 tail 추가 → `{US, Texas, California, ...}`
        - 3회차: head가 Texas인 것들의 tail 추가 → `{US, Texas, ..., Austin, ...}`
        - 새로 추가되는 행이 없으면 종료 → "미국 안의 모든 위치" 완성

    - 전체 구조: ① 두 나라 각각의 "안에 있는 위치 집합"을 재귀로 만들고 → ② born_in/lives_in 간선으로 사람 집합 2개를 만들고 → ③ 교집합(조인)
    - 결론: Cypher 4줄 = SQL 약 30줄. **데이터에 그래프형 질의가 많다면 처음부터 그래프 모델을 쓰는 게 낫다**는 근거

### Triple Stores와 SPARQL
- Property Graph와 표현력은 거의 동등하고, 표기 방식만 다른 모델
- 모든 데이터를 **(주어, 서술어, 목적어)** 3요소 튜플의 나열로 저장
    - (subject, predicate, object)
    - ex. (Elon, 소유한다, X)
- 주어 = 그래프의 정점
- 목적어는 두 가지 중 하나
    - ① 기본 타입 값(문자열, 숫자): 이때 서술어는 주어의 **속성(key-value)**
        - ex. (Elon, birthYear, 1971) → Elon 정점의 birthYear=1971 속성
    - ② 다른 정점: 이때 서술어는 두 정점을 잇는 **간선**
        - ex. (Elon, owns, X) → Elon → X로 향하는 owns 간선
- 즉, Property Graph의 "속성"과 "간선"이 Triple에서는 같은 문법으로 통일됨

- Turtle 표기법 (Notation3의 하위 집합)
    - Triple을 사람이 읽기 쉽게 쓰는 텍스트 형식

        ```turtle
        @prefix : <urn:example:>.

        _:taylor    a           :Person.
        _:taylor    :name       "Taylor".
        _:taylor    :bornIn     _:texas.

        _:texas     a           :Location.
        _:texas     :name       "Texas".
        _:texas     :type       "state".
        _:texas     :within     _:usa.

        _:usa       a           :Location.
        _:usa       :name       "United States".
        _:usa       :type       "country".
        _:usa       :within     _:namerica.

        _:namerica  a           :Location.
        _:namerica  :name       "North America".
        _:namerica  :type       "continent".
        ```
        - 한 줄 = Triple 하나. `_:taylor :name "Taylor"` = (taylor, name, "Taylor")
        - `a`는 "~의 타입이다(is a)"의 축약 서술어

### RDF (Resource Description Framework)
- Semantic Web
    - 2000년대 초반, 웹 페이지를 사람과 기계가 모두 읽을 수 있는 표준 형식으로 게시해 인터넷 전체를 하나의 데이터베이스처럼 만들려던 구상
    - 구상 자체는 정착하지 못했지만 유산이 남음
        - 연결 데이터 표준 JSON-LD
        - 생의학 분야의 온톨로지(Ontologies)
        - Wikidata 같은 지식 그래프(Knowledge Graph)

- RDF
    - 시맨틱 웹을 위해 설계된 Triple 데이터 모델. XML 또는 Turtle로 표기

        ```xml
        <rdf:RDF xmlns="urn:example:"
                xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#">

            <Location rdf:nodeID="Texas">
                <name>Texas</name>
                <type>state</type>
                <within>
                    <Location rdf:nodeID="usa">
                        <name>United States</name>
                        <type>country</type>
                        <within>
                            <Location rdf:nodeID="namerica">
                                <name>North America</name>
                                <type>continent</type>
                            </Location>
                        </within>
                    </Location>
                </within>
            </Location>

            <Person rdf:nodeID="Taylor">
                <name>Taylor</name>
                <bornIn rdf:nodeID="Texas"/>
            </Person>

        </rdf:RDF>
        ```

- RDF의 특징
    -  Triple의 모든 요소(주어, 서술어, 목적어)를 **URI로 표현**
        - ex. within 서술어 = `http://my-company.com/namespace#within`
    - 왜? 서로 다른 조직의 데이터를 합칠 때, 같은 단어(within, lives_in)가 다른 의미로 쓰였어도 네임스페이스가 달라 **충돌하지 않게** 하기 위함
        - `http://my-company.com/ns#within` ≠ `http://other.org/foo#within`
    - URI는 식별자일 뿐, 실제로 접속 가능한 주소일 필요는 없음 → 혼동을 피하려고 `urn:example:within` 같은 URN을 쓰기도 함

- SPARQL query language
    - "SPARQL Protocol and RDF Query Language", '스파클'로 읽음
    - ex. 대한민국에서 태어나 미국으로 이주한 사람 찾기:

        ```sparql
        SELECT ?personName WHERE {
            ?person :name ?personName.
            ?person :bornIn / :within* / :name "South Korea".
            ?person :livesIn / :within* / :name "United States".
        }
        ```
        - `?person`: 변수 (조건을 만족하는 값으로 채워짐)
        - `:bornIn / :within* / :name`: 서술어를 연쇄로 따라감 — bornIn 1번, within 0번 이상, name 1번
        
    - Cypher와 사실상 같은 표현:

        ```cypher
        (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location)    # Cypher

        ?person :bornIn / :within* ?location.                     # SPARQL
        ```

### Datalog
- 재귀적 관계형 질의(Recursive Relational Queries)
    - SPARQL·Cypher보다 오래된 언어 (Prolog 계열). 주류 DB에서는 드물지만 표현력이 매우 높음
    - 데이터 = 사실(Fact)의 나열. 관계형 테이블의 행에 해당

        ```prolog
        location(1, "North America", "continent").
        location(2, "United States", "country").
        location(3, "Texas", "state").

        within(2, 1).    /* US is in North America */
        within(3, 2).    /* Texas is in the US */

        person(100, "Taylor").
        born_in(100, 3). /* Taylor was born in Texas */
        ```

    - 규칙(Rule): 기존 사실로부터 새로운 사실을 도출 — 가상 테이블(Virtual Table) 생성
        - 문법: `결론 :- 조건1, 조건2, ...` = "조건들이 모두 참이면 결론도 참" (`:-`는 ←로 읽으면 됨)

        ```prolog
        within_recursive(LocID, PlaceName) :-
            location(LocID, PlaceName, _).          /* Rule 1 */

        within_recursive(LocID, PlaceName) :-
            within(LocID, ViaID),                   /* Rule 2 */
            within_recursive(ViaID, PlaceName).

        migrated(PName, BornIn, LivingIn) :-
            person(PersonID, PName),                /* Rule 3 */
            born_in(PersonID, BornID),
            within_recursive(BornID, BornIn),
            lives_in(PersonID, LivingID),
            within_recursive(LivingID, LivingIn).

        south_korea_to_us(Person) :-
            migrated(Person, "South Korea", "United States").    /* Rule 4 */
        ```
        - Rule 1 (기저): 모든 위치는 자기 자신 "안에" 있다 — Texas는 "Texas" 안에 있음
        - Rule 2 (재귀): LocID가 ViaID 안에 있고(within), ViaID가 PlaceName 안에 있으면(within_recursive), LocID도 PlaceName 안에 있다
            - "텍사스 ⊂ 미국"이고 "미국 ⊂ 북미"면 → "텍사스 ⊂ 북미"
        - Rule 3: 사람의 출생지가 BornIn 안에 있고 거주지가 LivingIn 안에 있으면 migrated
        - Rule 4: 그중 한국→미국인 경우만 추출
        - SQL 재귀 CTE의 "시작 집합 + 확장 규칙"과 동일한 구조 — Rule 1 = anchor, Rule 2 = 재귀 확장

    
    - ex. Texas가 미국과 북미에 속함을 재귀적으로 도출하는 과정

        ![alt text](image-6.png)
        - Rule 1 적용: 각 위치가 자기 자신에 속한다는 사실 생성 — (1, North America), (2, United States), (3, Texas)
        - Rule 2 1회 적용: within(2,1)에 의해 (2, North America) 추가, within(3,2)에 의해 (3, United States) 추가
        - Rule 2 2회 적용: within(3,2) + 방금 생긴 (2, North America)에 의해 (3, North America) 추가
        - 새 사실이 더 안 나오면 종료 → "Texas는 Texas·US·North America 안에 있다" 완성

## 이벤트 소싱(Event Sourcing)과 CQRS
- 이벤트 소싱
    - **현재 상태 대신, 상태를 만들어낸 사건(Event)들을 저장**하는 방식
    - 일반적인 방식: "잔액 = 5만 원" (상태를 덮어씀, 과거는 사라짐)
    - 이벤트 소싱: "입금 10만", "출금 3만", "출금 2만" (사건을 순서대로 기록, 현재 상태는 재생해서 계산)
    - 이벤트 로그의 규칙
        - append-only: 뒤에 추가만 함 → 쓰기가 단순하고 빠름
        - 불변(Immutable): 한번 기록된 이벤트는 수정·삭제하지 않음 (정정도 "정정 이벤트"를 추가)
        - 각 이벤트는 반드시 timestamp(또는 순번)를 가짐 — 재생 순서가 곧 정합성이므로

- 구체화된 뷰(Materialized View)
    - 이벤트 로그에서 파생시킨 **읽기 최적화 테이블**
    - 로그를 처음부터 재생하며 집계해 만든 "현재 상태의 스냅샷"
    - 읽기 요청은 로그가 아니라 이 뷰를 조회 (매번 전체 재생하면 느리니까)

- CQRS (Command Query Responsibility Segregation)
    - 쓰기 모델(이벤트 로그)과 읽기 모델(구체화된 뷰)을 **분리**하는 패턴
    - 쓰기는 append에 최적화, 읽기는 조회에 최적화 → 각자 자기 일에만 최적화된 구조를 가짐
    - "정규화=쓰기 최적, 비정규화=읽기 최적" 트레이드오프를 "둘 다 만들자"로 푸는 접근


- 예제: 컨퍼런스 예약 시스템
    - 이벤트 로그: 예약, 취소, 결제 이벤트가 발생 순서대로 쌓임
    - 하나의 로그에서 여러 구체화된 뷰를 생성:
        - 뷰 1: 현재 잔여 좌석 수 (예약 -1, 취소 +1로 집계한 현재 상태)
        - 뷰 2: 시간대별 예약 추이 차트 (분석용)
    - 장점
        - 나중에 새로운 분석이 필요하면 **로그를 다시 재생해서 새 뷰를 만들면 됨** — 과거가 전부 보존되어 있으므로
    - 주의점
        - 이벤트 재생은 순서에 민감함
        - timestamp 순서대로 처리해야 하는 오버헤드
        - 재생 중 외부 테이블과 조인하면 위험
            - 그 테이블의 **현재** 상태와 조인하게 되어, 이벤트 발생 **당시** 상태와 달라 결과가 원본과 어긋날 수 있음 (재현 불가능성)
        - → 재생에 필요한 정보는 가능한 한 이벤트 자체에 담아두는 것이 원칙

## Dataframes, Matrices, and Arrays
- 데이터프레임: 분석과 머신러닝을 위한 데이터 모델
    - Python Pandas, Apache Spark(DataFrame API), R 등
- 관계형 테이블과 유사하지만(행×열), 질의가 아니라 **변환 연산의 연쇄**로 데이터를 다룸
    - 희소 배열(Sparse Arrays) 지원 — 대부분 0인 행렬을 효율적으로 저장 (추천 시스템의 유저×아이템 행렬 등)
    - 벡터화 연산(Vectorized Computation) — 행 단위 반복문 대신 컬럼 전체에 한 번에 연산
- ML 파이프라인에서 관계형 데이터 → 행렬(모델 입력)로 변환되는 중간 지점의 모델
